# Current Architecture

## Runtime shape

Vendo is a server-rendered Laravel application. `routes/web.php` defines public pages and role-area routes; controllers coordinate request validation and Eloquent queries; Blade views render the role-specific pages. Vite builds CSS and JavaScript under `resources/`. The existing buyer and admin pages are primarily Blade; the seller Orders screen also uses JavaScript to refresh rows and load an order drawer.
The public Terms and Privacy routes render repository Markdown through a shared legal Blade page. Buyer, Seller, and Logistics Center web registration forms link to those routes; their required checkbox does not yet store a versioned acceptance record.

## Main domains

- **Identity:** one `users` table with role/status/account-state fields; role-specific data is held in profile tables. Separate admin authentication guard exists.
- **Authentication:** Buyer, Seller, and Logistics browser login support password sessions and Google Identity Services. Laravel validates Google ID-token signatures and claims against cached Google JWKS and configured OAuth client IDs. New Google identities continue through their normal registration form with a short-lived role/email proof; Google does not bypass profile requirements or account approval. Rider mobile supports email OTP registration, password/Google login, and email-code password reset through `/api/v1/rider`. Google JWT verification uses `firebase/php-jwt`; Firebase Auth or database services are not used.
- **Commerce:** categories, products/images, cart items, orders/items, and order status events. Checkout accepts selected buyer-owned cart lines, creates one order per seller represented in that selection, leaves unselected lines in the cart, and snapshots a server-quoted shipping fee and actual facility route for each Seller order. Buyers can optionally send a device location pin with checkout; it is stored per order and exposed only to the assigned delivery Rider. Buyer saved items and appearance/sound settings now use Buyer-scoped database rows; older browser-local choices are imported once.
- **Operations:** The approved hierarchy is Logistics Company → Province Hub → Station Hub; multiple companies may cover one province. Additive migrations backfill company/facility links and add primary municipality coverage, staff, Rider tasks, Transport Driver/vehicle/trip manifests, real order stops, manual handoffs and internal Logistics messages. Authenticated `/logistics/portal/*` pages persist facility setup, Rider/Driver review, station pickup/delivery assignment, trip departure/arrival, hierarchy camera scans, messages, account updates, reports, exceptions and cross-company manifests. The Superuser assigns primary coverage where companies overlap. Preserve virtual SH/SH scanner records for historical orders. Rider/Driver interfaces stay in the separate mobile repository.
- **Platform operations:** notifications, announcements, platform policies, conversations/messages/attachments, complaints/evidence/activity, compliance warnings/violations, fixed 10% Admin merchandise commission calculations, Seller category requests, Seller voucher records/redemptions, order shipping accrual records, and admin login-session records. The legacy commission setting row is no longer used in calculations. Rider and Transport Driver APIs report their own accrued route-stop earnings; payout execution is not implemented. Case conversations use the existing nullable `conversations.complaint_id`, with one private thread per Buyer/Seller participant.

## Request flow

Browser → named web route → middleware/guard → controller validation and actor-scoped query → transaction/model changes → Blade or JSON partial response → browser update. Google browser credentials are sent to Laravel and verified server-side; the browser never decides that an email is verified. The separate Flutter rider client calls `/api/v1/rider` JSON routes. The separate Flutter buyer client calls `/api/v1/buyer`, which issues 30-day `buyer:shop` Sanctum tokens to approved buyers and re-checks approval on every request through `EnsureApprovedBuyerToken`; its checkout shares `BuyerCheckoutService` and `CheckoutRevisionService` with the web checkout so both channels create identical COD orders. See the [Buyer mobile API spec](features/buyer/mobile-api/spec.md). Public registration requires a server-issued email OTP or Google proof bound to the normalized email, validates PSGC residence, and matches a unique approved, active center; approved login issues seven-day, `rider:scan` Sanctum bearer tokens. The API checks approval, active account and center membership, and order assignment on every scan; the client itself is in the separate E-Comm_Mobile repository.

The legacy authenticated `/logistics/facilities` web routes and `/api/v1/rider/facility-scans` workflow remain for older assignments. New `/logistics/portal/{station|province}/scans` endpoints resolve the facility from the approved session, lock the order and enforce stop order plus scheduled trip or manual handoff. Open parcel exceptions block scans and trip departure. New facility-routed Rider completions require the authenticated proof endpoint and private photo storage; the Flutter Rider client still needs to adopt that contract. The separate E-Comm_MSA Flutter client and `/api/v1/sh-scanner` API remain a paused legacy virtual-checkpoint workflow; their tables/events are retained.

## Key boundaries

- `users.role` identifies buyer, seller, logistics center, province/Station Hub staff, Rider (`courier` legacy value), Transport Driver, or admin. The database role column is a string.
- Registration status and account status are different concepts. Current registration state includes pending/approved/disapproved; administrative state also includes suspension/deactivation fields.
- Orders are shared across buyer/seller and use facility stops, RiderTasks, and manifest trips for newer Logistics flows. Checkout blocks an address whose seller/buyer Station route cannot be uniquely resolved.
- Communications and notifications are reusable tables/models, but no push-notification delivery service is documented as implemented.

## Current constraints

Most functionality is in the web route/controller layer. The buyer mobile API covers the storefront, cart, COD checkout, orders, saved items and notifications; its Flutter screens are connected but owner device verification is pending, and voucher selection, order reviews, profile editing and list paging are not wired in the app yet. The Rider API still serves legacy Truck and local Rider assignments while the new Station task, trip, exception, and proof contracts are integrated with the separate mobile app. Transport Driver registration is available, but Driver mobile login/trip execution is pending. `/api/v1/sh-scanner` remains a legacy checkpoint contract and is not used for new facility stops. Rider and Transport Driver interfaces are mobile-only. Logistics Messages and Reports use scoped server data; Company Reports include shipping settlement/accrual summaries, while payout execution, cross-company remainder allocation, SLA calculations, and PDF/Excel exports are not implemented. CSV exports are available. The Logistics bell uses short polling. Some role routes need a security review and owner end-to-end verification. See the [status matrix](domain-feature-status.md), [registration contract](features/courier/registration-api/spec.md), and [rider scan contract](features/courier/scan-api/spec.md).

Production web domain: `vendo-ph.app`; hosting is Azure behind Cloudflare Tunnel. Set `APP_URL=https://vendo-ph.app`, `SESSION_SECURE_COOKIE=true`, and `TRUSTED_PROXIES` to the actual comma-separated reverse-proxy IPs/CIDRs that connect to Laravel. Rebuild cached config during deployment. The location catalog is bundled, so province/city checkout and routing need no runtime PSGC request. Rider registration also uses a bundled barangay snapshot through the versioned API; the older web registration forms still fetch barangays from the external PSGC mirror.

An optional `nixpacks.toml` was added for Railway. Its start command runs `php artisan migrate --force` automatically and starts the development Artisan server. It is not the documented Azure production path; review and change the startup/migration strategy before using it against a live database. The old `/logistics-preview/*` route and fixture files remain in the repository but are no longer mounted; only the protected `/logistics/portal/*` routes serve the new hierarchy UI.

Address map pins additionally require `GEOAPIFY_API_KEY` in Laravel's deployment environment. Geoapify supplies the raster map tiles and both forward/reverse geocoding; restrict the browser key to the site's referrers. It has a free usage tier, unlike the Google Maps APIs. Google sign-in additionally requires `GOOGLE_WEB_CLIENT_ID` and `GOOGLE_ALLOWED_CLIENT_IDS` in Laravel's deployment environment. Configure the deployed origin and local development origins in the Google OAuth project; keep OAuth client secrets out of source control. Details and the native app setup are in the [Google sign-in spec](features/shared/google-auth/spec.md).
