## Fixed "That municipality is outside Abra" when creating a Station Hub

Creating a Station Hub from Province Hub > Station Hubs (`POST /logistics/portal/province/stations`) rejected every municipality with *That municipality is outside Abra. Pick one from the list.* even for a municipality that belongs to the hub's province, such as Bangued.

**Cause:** `LocationCatalog::codesForNames()` builds its codes from the bundled `resources/data/psgc-locations.json`, whose keys are PSGC codes. `json_decode(..., true)` turns numeric-looking object keys into PHP **ints**, so the method returned `[140100000, 140101000]`. `PortalController::createStation()` then checks the pair against the hub with a strict comparison (`$codes[0] === $hub->province_code`), and the hub's `province_code` column is a `string(9)`, so `'140100000' === 140100000` was always false and the request aborted with 422. Other call sites (checkout routing, address resolver, buyer location API) already cast the codes back to strings, which is why only this screen broke.

**What changed:** `app/Services/LocationCatalog.php` — `codesForNames()` now returns both codes as 9-digit strings, so the strict check matches the way the codes are stored everywhere. No schema, route, guard or copy changes.

### Verified

- `php -l app/Services/LocationCatalog.php`: clean.
- Through `php artisan tinker`: `codesForNames('Abra', 'Bangued')` returns `['140100000', '140101000']`; the Abra Hub (id 8) compares equal to the province code (`true`), Bangued has no active Station Hub yet, `codesForNames('Laguna', 'Santa Cruz')` still resolves to string codes, a mismatched pair (`Abra` + `Manila`) still returns null, and `municipalityCoordinates('Abra', 'Bangued')` still resolves to 17.6083 / 120.6381.

## Google sign-in can list one Android client per app package

Both mobile apps send the website's web client as `serverClientId`, so an Android token arrives with that web client as `aud` and the package's own Android client as `azp`. `GoogleIdTokenVerifier` requires every ID it sees to appear in `allowed_client_ids`, but the config could hold only one Android ID (`GOOGLE_ANDROID_CLIENT_ID`) — not enough for `com.example.vendo_buyer` and `vendoph.rider` at once.

**What changed:** `config/services.php`

- A `$clientIds()` helper splits a comma-separated env value, trims it, and drops empty and duplicate entries.
- `android_client_ids` and `ios_client_ids` (previously the singular `android_client_id` / `ios_client_id`, which nothing else read) are now arrays built from the same env var names, so `GOOGLE_ANDROID_CLIENT_ID=id1,id2` lists both packages' clients.
- `allowed_client_ids` keeps its behaviour: `GOOGLE_ALLOWED_CLIENT_IDS` overrides, otherwise the web client plus every listed Android/iOS ID.

`.env` (local only, never committed): the stale `GOOGLE_ANDROID_CLIENT_ID` from project `311754374460` was emptied while this change was made, and the stray duplicate `GOOGLE_ANROID_CLIENT_ID` line was removed. The owner then put that same `311754374460` client back, alongside the `468116080938` web client, to test the pair. The two IDs sit in different Google Cloud projects, which Android sign-in rejects (`[28444]`), so that value is a test artefact until clients exist in `468116080938`.

**Plan settled:** register both packages in project `468116080938`, the project that already owns the working web client and the site's authorized origins, instead of moving every client to `vendo-mobile-514813`. That leaves the website's configuration untouched.
