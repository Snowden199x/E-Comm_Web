## Buyer and Seller account deletion requests with Admin review

**What changed**

- New table `account_deletion_requests` (migration `2026_11_11_100000_create_account_deletion_requests_table.php`) storing the requesting user, JSON reasons, optional comment, status (`pending`/`approved`/`rejected`), request time, reviewing Admin and time, and the Admin note. Indexed on `(user_id, status)`.
- New `App\Models\AccountDeletionRequest` (reason list, statuses, `user`/`reviewer` relations, `pending` scope, `isPending`). `User` gained `deletionRequests`, `latestDeletionRequest` and `pendingDeletionRequest`.
- Buyer Account → *Privacy and terms* has a **Delete account** card. **Request deletion** opens an Alpine dialog (teleported to `<body>`): required reason radio plus optional comment (max 500, required for *Other*). Posts to `buyer.account.deletion-request` (`throttle:5,1`), returns with a success banner. While a request is pending the button is disabled and the sent date is shown. Validation errors reopen the dialog.
- Seller Account → *Security* has the same card with a native `<dialog>` (`ac-del` styles in `resources/css/seller/account.css`, open/close in `resources/js/seller/account.js`). Posts to `seller.account.deletion-request`.
- Admin User Management profile modal: a **User request for deletion of account** bar now sits under Suspend/Deactivate (and under Activate), with a *Pending* pill when one is waiting. It opens `deletion-request-modal.blade.php`: reasons, comment, requested date, and the reviewer/note once decided — or an empty state when the user never asked. While pending, Admin can **Approve deletion** (request `approved` + `account_status = deactivated`) or **Reject request** with an optional note.
- Both Admin decisions run in a transaction with an `admin_action_logs` row (`deletion_approved`, `deletion_rejected`) and show the shared confirmation banner. The user-management query eager-loads the new relations so the list and dialogs stay in sync.
- Requests are server-validated (`Rule::in` on the reason list, comment length, `Other` requires a comment) and scoped to the signed-in Buyer/Seller; the Admin endpoints check role, approved status and that a pending request exists.

**Why**

Users had no way to ask for their account to be closed, and Admin had no place to see or decide such a request. Keeping the decision with Admin matches the existing suspend/deactivate pattern.

**Practical effect**

A Buyer or Seller can submit one pending deletion request with a reason and comment. Admin sees it inside the existing user-management profile modal and either closes the account (it can no longer sign in; orders, products and messages stay) or rejects it. Nothing is deleted at request time.

## 7-day return window and the two-attempt delivery rule

**What changed**

- **Return window:** `OrderReturnService::RETURN_WINDOW_DAYS = 7` with `canRequest()` / `windowClosesAt()`. A request is accepted only within 7 days of `delivered_at` (checked on the form route, under the order lock when the request is created, and used by the order page). The Buyer order page shows the closing date and replaces the **Request a return** button with a note when the window has passed; the form page repeats the date. Seller approval is not windowed, so a request made in time can still be decided later.
- **Delivery attempts:** new `orders.delivery_attempts` counter (migration `2026_11_11_150000_add_delivery_attempts_to_orders.php`, default 0) and `DeliveryCutoff::MAX_DELIVERY_ATTEMPTS = 2`.
  - First failure at the cutoff: attempt 1 is recorded, the order becomes `delivery_failed`, the status note says the parcel returns to the destination Station Hub for one final attempt, and the Buyer gets a notice explaining the return to the hub and that a second failure cancels the order. Rider and hub notices say the same.
  - Second failure (still `out_for_delivery` at a cutoff with one attempt used), or a parcel still `delivery_failed` after the next day: `cancelUndelivered()` runs under the row lock. It restores every item quantity through `InventoryService` (type `cancellation`), sets the order to `cancelled`, voids the Seller voucher, writes a status event naming the holding hub, and notifies the Buyer, Seller, assigned Rider (`shipment_cancelled`) and destination hub. A rescheduled parcel is `assigned_to_rider`, so it is not caught by the stale check.
- **Rider reschedule** now refuses a parcel that already used its final attempt (409) and its notifications say this is the final attempt.

**Why**

The owner asked for a hard 7-day return limit and a two-attempt delivery policy: one failed attempt returns the parcel to the Buyer's nearest (destination) Station Hub, the next day is the final attempt, and another failure cancels the parcel automatically.

**Files:** `app/Services/OrderReturnService.php`, `app/Services/DeliveryCutoff.php`, `app/Http/Controllers/Buyer/OrderController.php`, `app/Http/Controllers/Api/RiderDeliveryRescheduleController.php`, `app/Models/Ecommerce/Order.php`, `resources/views/buyer/orders/show.blade.php`, `resources/views/buyer/orders/return.blade.php`, `database/migrations/2026_11_11_150000_add_delivery_attempts_to_orders.php`.

**Docs:** [return request spec](../features/shared/order-return-request/spec.md), [delivery window spec](../features/courier/delivery-window/spec.md), `docs/schema.md` and `docs/domain-feature-status.md`.

**Effect:** a return request older than 7 days is refused server-side, not just hidden. A parcel now has at most two closed attempts; the second cancels it, puts the stock back and leaves no cash to refund because COD was never collected. The order drops out of Seller/Rider earnings because it is `cancelled`.

**Verification:** `php -l` on every changed PHP file; `migrate --pretend` printed the single column, then the migration was applied on the local dev database; `view:cache` compiled every Blade template. No cutoff sweep, reschedule, cancellation or browser page was exercised, so the attempt counting, stale cancellation, stock restoration and notifications are unverified at runtime.

**Known gaps:** the parcel's physical return to the hub is recorded in the status note and notifications only (no scan or custody row); attempts are counted when the day closes, not at the doorstep; there is no Admin override to extend the return window or grant a third attempt.

## Limit surfacing, Admin overrides and the Rider return-to-station scan

**What changed**

- **Limits in the UI.** The Buyer order page now shows `delivery_attempts of max` (with "no attempts left" or the next scheduled date) in the tracking card, and the return card shows the window closing date plus the days left; the return form repeats the countdown. The Seller order drawer shows the delivery attempt count and, for delivered orders, the return deadline.
- **Admin overrides** (`admin.limit-overrides.index|attempt|window`, Admin sidebar **Limits & Overrides**): search by `VN-xxxxxx` or tracking number, or see the last 30 orders that have attempts, an override or a return request. *Grant one more attempt* is limited to `delivery_failed`/`assigned_to_rider` with at least one failure and at most 3 extras; it increments `delivery_extra_attempts`, restarts the next-day clock and notifies the Buyer, Rider and hub. *Extend return window* takes a later date and a note, stores `return_window_until` at end of day and notifies the Buyer. Every override writes an `order_status_events` note naming the Admin and the reason, and stores `limit_override_by|at|note` on the order.
- **Effective limits read the overrides:** `OrderReturnService::windowClosesAt()` returns the later of `delivered_at + 7 days` and `return_window_until` (plus `daysLeft()` for the countdown); `DeliveryCutoff` and the Rider reschedule guard use `2 + delivery_extra_attempts`.
- **Rider return scan** (`POST /api/v1/rider/deliveries/{order}/return-scan`, token + approved rider, body `tracking_number` + `scan_key`): the Rider scans the parcel back at the destination Station Hub after a failed attempt. It writes one `order_scan_events` row (`returned_to_station`), a status-event note naming the hub, notifies Buyer/Seller/hub, stays idempotent on `scan_key`, keeps the order `delivery_failed` so the next attempt can be booked, and returns attempts used/remaining. Built like the existing scanner endpoints; the mobile app change is in the separate repository.

**Why**

The owner asked to surface both limits, let Admin override them with an audit trail, and make the physical return to the hub a real scan in the Rider app (same scanner pattern) instead of a status note.
