# Progress log: 30 October 2026

## Rider notification API and assignment alerts

- Added `app/Http/Controllers/Api/RiderNotificationController.php`:
  - `GET /api/v1/rider/notifications` returns only the signed-in Rider's rows, newest first (50 max), with `unread_count` and `latest_id`. `?since=<id>` returns only newer rows, so the mobile app can poll cheaply.
  - `POST /api/v1/rider/notifications/{notification}/read` marks one row read; another Rider's row returns 404.
  - `POST /api/v1/rider/notifications/read-all` marks every unread row read.
- The three routes sit inside the existing `auth:sanctum` + `EnsureApprovedRiderToken` group, so only an approved Rider with an active logistics membership can use them.
- Main Hub assignments now notify the assigned Rider (`DispatchController`): pickup courier, single and bulk delivery, and Truck linehaul. Station Hub pickup/delivery assignment already created `rider_task_assigned`; the 60-minute pickup expiry continues to notify the Rider and the assigning staff member.
- Added `tests/Feature/RiderNotificationApiTest.php` (6 tests, 22 assertions): own rows only, newest-first feed and unread count, `since` watermark, single read, foreign-row 404, read-all, and no-token rejection.
- No migration: `notifications` already has `user_id`, `type`, `title`, `message`, `link` and `read_at`.
- Updated the courier notification spec, domain status, testing doc, and this log.
- Corrected `docs/features/courier/scan-api/spec.md`: Station Hub cash receipt is implemented, so `GET /api/v1/rider/cash` does drop the amount after the hub confirms. The Rider app now consumes that endpoint on its Earnings screen.

**Verified:** `php artisan test` -> 40 passed, 5 failed. The 5 failures are the pre-existing `GD extension is not installed` registration tests, unchanged by this work. `php -l` clean on the controller, dispatch controller and route file. The running local server answers the new route (401 without a token), and `php artisan route:list` shows all three routes.

**Known gaps**

- Not push: a closed app receives nothing until it opens and polls.
- The shared `notifications.link` column is not used by the Rider app yet; there are no deep links from a notification to a specific parcel.
- Device acceptance testing of the mobile polling/banner is the owner's.

## 5:00 PM delivery cutoff and rider reschedule

- Added `config/delivery.php` (`DELIVERY_CUTOFF`, default `17:00`) and `App\Services\DeliveryCutoff`. Once the cutoff passes, a lazy sweep marks every order still `out_for_delivery` as `delivery_failed`, sets `delivery_failed_at`, writes a status event, notifies the Rider (`delivery_window_closed`) and the destination Logistics Center, and lets the existing Order listener update Buyer and Seller and the parcel conversation. COD cash stays `not_collected`.
- The sweep runs before the Rider assignments response and the Station Hub operations list; `routes/console.php` also schedules it daily at the cutoff, so a host with the scheduler closes the window even when nobody is looking.
- `OrderScanWorkflow` now rejects `out_for_delivery` and `delivered` after the cutoff, and rejects `out_for_delivery` before `delivery_scheduled_for`. This closes the stale-screen gap: a Rider cannot complete a handover after 5:00 PM even if the app still shows the old button.
- Added `POST /api/v1/rider/deliveries/{order}/reschedule` (`RiderDeliveryRescheduleController`). It accepts a failed parcel assigned to that Rider, returns it to `assigned_to_rider`, sets `delivery_scheduled_for` to tomorrow, records a status event, and notifies Buyer, Seller and the Station Hub. It saves quietly so the generic rider-assigned message is not repeated.
- The assignment response now includes `delivery_window` (`cutoff_label`, `deadline_label`, `closed`, `scheduled_for`, `scheduled_for_label`, `reschedulable`), and `delivery_failed` parcels stay in the Rider's delivery list.
- Migration `2026_10_30_100000_add_delivery_window_to_orders.php` adds `delivery_scheduled_for` and `delivery_failed_at`; applied to the local database.
- Added `tests/Feature/DeliveryCutoffTest.php` (6 tests): failure after the cutoff with notifications, nothing before 5:00 PM, scan rejection after the cutoff, reschedule to the next day, scan rejection before a scheduled day, and the failed parcel staying in the rider list as reschedulable.

**Verified:** `php artisan test --filter=DeliveryCutoffTest` -> 6 passed (27 assertions). `php -l` clean on every changed PHP file. `php artisan route:list --path=rider/deliveries` shows the reschedule route, `php artisan schedule:list` shows `close-delivery-window` at 17:00, and `php artisan migrate` applied the new columns.

**Known gaps**

- The cutoff uses the app timezone (`Asia/Manila`) for every hub; it is not configured per station.
- The cutoff applies to every parcel out for delivery, including one dispatched minutes before 5:00 PM.
- Rescheduling always books the next day, and a failed parcel keeps its Rider; the Station Hub cannot reassign it to a different Rider yet.

## Transport Driver applications: apply-to choice and hub review split

- A Transport Driver now chooses **who reviews the application** — Station Hub only, Province Hub only, or both — in the Driver app. Station-only drivers are approved by their Station Hub and work station to station. Province and both drivers are approved by the Province Hub only; the Station Hub lists them read-only as *Waiting for Province Hub approval*. The rules and the API contract are in [transport driver applications](../features/logistics/transport-driver-applications/spec.md).
- Migration `2026_10_30_120000_add_application_scope_to_transport_driver_details.php` adds `apply_to`, `station_hub_id`, `approved_by`, `approved_at`, `vehicle_type` and `plate_number`. **Not yet run on the owner's database.**
- `TransportDriverRegistrationController` stores the apply scope, derives the Province Hub from a chosen Station Hub, records the declared vehicle, and notifies only the reviewing hub (plus a read-only notice to the linked Station Hub for `both`). It now also serves `/locations`, `/{cityCode}/barangays` and `POST /application-status` for the app.
- `App\Services\StationHubResolver` links province/both drivers to the Station Hub that covers their municipality, else the nearest Station Hub by municipality-centre distance, else one in the chosen hub's network. It never falls back to an arbitrary facility.
- Station Hub gained **Drivers** under People (`lgp.station.drivers`, plus review/status/document routes) with Driver Approval tabs, details and documents. Approve / Reject appears only for station-only applicants; province/both rows show the read-only waiting state. The Province Hub *Transport Drivers* page now shows *Applied to* and the linked Station Hub, and only reviews province/both applications. Both review paths lock the driver and user rows and set `approved_by` / `approved_at` on approval.
- Sign-in now explains an unapproved application: `POST /api/v1/transport-drivers/login` returns `403` with `status` (`pending` / `rejected`), the reviewing hub and the rejection reason for a valid applicant, and `TransportDriverAccessService` accepts a driver whose reviewing hub (Station Hub for station-only) and company are active. A station-only driver is no longer offered in *Create trip*.
- Mobile side lives in `E-Comm_Mobile/vendo_driver` (rider-style registration wizard, Apply-to step, API client, status sheet, sign-out clears the token).

**Verified (static only, owner testing pending):** `php -l` clean on every changed PHP file; `php artisan view:cache` compiled the new and edited Blade pages (then cleared); `php artisan route:list` shows the four station driver routes and the new driver API routes; `flutter analyze` in `vendo_driver` reports no issues. No automated tests were added or run, per the repository rules.

**Known gaps**

- `StationHubResolver` matches on municipality centres, not road distance, and a Province Hub may still re-link a driver.
- A rejected applicant cannot re-apply with the same email.
- The Driver app's trip screens still read demo data; only registration, approval status and sign-in call the API.

## Transport Driver API: session profile and password recovery

- Added `GET /api/v1/transport-drivers/me` (`TransportDriverApiController@me`) behind
  `auth:sanctum` + `EnsureApprovedTransportDriverToken`. It returns the same `driver`,
  `province_hub`, `station_hub`, `reviewing_hub` and `company` shape as `POST /login`, so the Driver
  app can restore a saved token and show the profile the hub actually approved. Both responses now
  come from one `profilePayload()` helper, so they cannot drift apart.
- `POST /login` therefore returns more fields than before: the driver's email, phone, licence
  number/category/expiry, vehicle type, plate and status, plus the hubs' province and municipality.
  The existing keys are unchanged, so an older build still reads the response.
- Added `app/Http/Controllers/Api/TransportDriverPasswordResetController.php` with
  `POST /api/v1/transport-drivers/password/otp/send`, `/password/otp/verify` and `/password/reset`,
  mirroring the Rider reset flow. It only matches `transport_driver` accounts, answers identically
  for an unknown email, and uses its own `driver:password:*` cache keys so a Rider code cannot reset
  a driver password. A successful reset revokes every token for that driver.
- Fetching a driver profile requires an active reviewing hub and company, matching sign-in, so an
  expired licence suspends access on the next app start rather than at the next password change.
- No migration and no new dependency.

**Verified:** `php -l` clean on both changed controllers and `routes/api.php`;
`php artisan route:list --path=transport-drivers` shows all 17 routes including `me` and the three
password routes. Live checks against the running server: `GET /me` without a token -> 401;
`password/otp/send` for an unknown email -> 200 with the neutral message; `password/otp/verify` with
a wrong code -> 422; `password/reset` with a bogus token -> 422. A temporary approved driver was
created to exercise `GET /me`, which returned the full profile payload, then removed together with
its token and detail row (database left with zero driver rows and zero details). No automated tests
were added or run, per the repository rules.

**Known gaps**

- Mail delivery of the reset code depends on the existing mail configuration; without it the send
  endpoint still answers 200 and only the log shows the failure.
- The seven-day token expiry is unchanged; there is no refresh token or device list.
- Revoked rows stay until `personal_access_tokens` cleanup runs; tokens are deleted on reset, but an
  unreachable device keeps a stale copy until its next request is rejected.
