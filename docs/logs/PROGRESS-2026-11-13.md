# Progress 2026-11-13

## Buyer: Support restyle

**What changed:** The three Buyer support pages (`buyer.support.index`, `.create`, `.show`) use the pastel lilac system from the Seller area. Routes, data and ticket rules are unchanged.

- **List.** Four stat cards became status chips with counts (All, Open, In review, Resolved). A search by subject or ticket number runs on Enter. Each row has a status tile, a **View thread** button and the last activity. Filtering and paging load without a full reload, with shimmer rows while loading and an error state with **Retry**. Empty states: no requests yet, and no requests match your filters (**Clear filters**).
- **New request.** Topic and Order dropdowns are styled menus over the native selects (searchable Order list, keyboard support, bottom sheet on phones). Attachments use a drop area with file chips and a check for type, size and the 2-file limit before sending. Subject and message are checked in the browser first, with a message that says how to fix it.
- **Thread.** Pastel bubbles, status badge, **Mark as resolved** opens a dialog instead of the browser confirm.
- **Status colors.** Open = lilac, In review = sky, Resolved = mint.
- **Messages.** Success and error messages use the top banner (existing `$store.banner`).
- **Controller (`Buyer\SupportTicketController`).** `index` accepts optional `?status=` and `?q=` (max 100 characters) and passes both to the view. Validation messages now say what happened and how to fix it. Closing an already resolved ticket returns a validation message instead of a bare 409 page.
- **Assets.** New `resources/css/buyer/support-theme.css` and `resources/js/buyer/support.js`, registered in `vite.config.js` and loaded from the three views.

**Not verified:** no PHP or browser run. Run `npm run build`, then check each status chip, search by subject and by `#id`, paging with a filter, a new request with errors and with files (wrong type, over 5 MB, three files), reply, Mark as resolved, and the phone layout.

## Seller: Returns restyle

**What changed:** The Seller Returns page (`GET /seller/returns`, route `seller.returns.index`) uses the same pastel lilac system as Delivered orders. Approve, decline and mark-received rules are unchanged.

- **View.** `resources/views/seller/returns/index.blade.php` rewritten. The two tables (waiting, recently handled) became one list with status chips and counts (All, Waiting for you, Approved, Declined), a search by order or buyer that runs on Enter, and a reason select that applies on change. Columns merged to Order (with requested date), Buyer, Reason, Refund, Status and Actions. Three tiles: waiting for you, on the way back, refunded.
- **Actions.** Every waiting row has **Approve return** and **Decline**; an approved return that the rider has picked up has **Mark received**; other rows have **View details**. One click on a row opens a side panel with the items, buyer's details, refund, return trip and your note.
- **Dialogs.** Approve and Mark received ask for confirmation. Decline asks for a reason (checked in the browser first, with quick-fill reasons) and reopens with the typed text after a server error.
- **Status colors.** Waiting for you and waiting for rider pickup = butter, on the way back = sky, handed back = mint, declined = rose, approved but not scheduled = lilac.
- **States.** No requests yet, no requests match your filters (**Clear filters**), shimmer rows while filtering or paging, an error state with **Retry**, and a spinner on the dialog buttons. Messages show in the top banner.
- **Controller (`Seller\ReturnRequestController`).** `index` accepts optional `?status=` (pending, approved, declined), `?reason=` and `?q=` (max 100 characters), pages at 15 with waiting requests first, and passes counts. The old list was all waiting plus the last 30 handled. `approve`, `reject` and `received` now turn the 409 and 422 refusals from the services into a banner message that says how to fix it; other errors keep their normal pages. Decline validation messages reworded.
- **Assets.** New `resources/css/seller/returns-theme.css` and `resources/js/seller/returns.js`, registered in `vite.config.js`. The page no longer uses the undefined `do-btn--danger-soft` and `do-badge--lilac` classes.

**Not verified:** no PHP or browser run. Run `npm run build`, then check each chip, search by order and by buyer name, the reason select, paging, Approve, Decline with a short and a valid reason, Mark received on a picked-up return, the details panel, and the phone layout.

## Admin: Deletion requests restyle

**What changed:** The Admin deletion request panel (opened from a Buyer or Seller profile in User management) follows the Admin design system. Routes, data and decisions are unchanged.

- **Panel (`user-management/partials/deletion-request-modal`).** Header with the user's avatar, role and a status pill; body with requested date and wait time (amber from 3 days), reasons, the user's words, and a two-line summary of what Approve and Reject do. A reviewed request shows who reviewed it, when, and the note.
- **Decision flow.** The footer shows **Reject request** (danger pastel) and **Approve deletion** (success pastel). Approve asks to confirm first ("Close <name>'s account?") with **Approve and close account**, because it deactivates the account. Reject reveals the optional note with a 500-character counter. Both have **Go back**, and the panel resets when closed. Submit buttons get the standard spinner from `button-loading.js`.
- **Profile bar (`profile-modal`).** Label is **Review deletion request** while pending (amber border), **View deletion request** after a decision, **Deletion request** when none.
- **Result popup (`confirmation-modal`).** Shorter wording for deletion approved and rejected.
- **Controller (`Admin\UserManagementController`).** If another admin already handled the request, approve and reject return to the page with an error banner that says what to do, instead of a 404 page. The note-too-long message says how to fix it. Decisions, transactions and `admin_action_logs` entries are unchanged.
- **Docs.** `docs/features/shared/account-deletion-request/spec.md` has a new dated section.
- **Assets.** No new CSS or JS.

## Admin: Limits and overrides restyle

**What changed:** The Admin Limits and overrides page (`admin.limit-overrides.index`) follows the Admin design system. The rules (7-day return window, 2 attempts plus up to 3 extra), notifications, order timeline entries and audit log are unchanged.

- **States.** No orders need an override, and no order matches the search (**Clear filters**).
