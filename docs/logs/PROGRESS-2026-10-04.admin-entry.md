# Progress — 4 October 2026

## Admin: Registrations and User Management UI redesign

- Redesigned Admin **Registrations** (list and details) and **User Management** (list and profile modal) from the owner's mockups. Presentation only: no controller, route, model, migration, or schema changes. The Admin shell (sidebar, top bar, notification bell) is unchanged.
- **Registrations list:** pending-count cards that also filter the table by user type, pill-style search, date and user-type filters, role chips, boxed pagination with a windowed page list, "Showing 1–8 of N entries", and an empty state with "Clear filters". Search, filters, and paging refresh the table in place with a loading bar, a request-cancel guard, and a row reveal; the URL is kept in sync with `history.replaceState`. Fixed a latent bug where pagination links rendered after an AJAX refresh pointed at the bare `/registrations/table` partial; page buttons now use `data-page` and the same fetch.
- **Registration details:** profile card plus sliding-pill tabs (Personal Information, User Address, and Business Information for sellers and logistics centers) with cross-fading panels, keyboard arrow navigation, ID preview with click-to-enlarge viewer and a "preview unavailable" fallback, and a sticky Reject/Approve bar. Street and house number are shown as one "Street / House No." line. Approve now asks for confirmation (it sends an email); both dialogs disable the submit button while sending to prevent double submits. The reject reason options are unchanged; choosing "Other" requires details client-side only.
- **Result dialog copy corrected:** the old rejection dialog said an email would be sent to the applicant. The backend does not send one (`RegistrationController::disapprove` only stores the reason; the applicant sees it at login). The new copy says the reason was saved and will be shown at the next sign-in. Approval copy still says an email was sent, which is true.
- **User Management list:** same list pattern, plus a "Rejected users" toggle. Filters and paging now swap `#um-region` (table and per-user modals together) from the index response instead of reloading the page, so each row's modals always match the visible rows. Status pills: Active, Suspended, Deactivated, Rejected.
- **User Management profile:** remains a **modal only** (not a separate page), per the owner's note. Left card with role, status, contact, business, colored category chips, and Date Joined; Suspend/Deactivate (or Lift suspension/Activate) under the card; Personal Information, Address, and Business Information stacked on the right. House number and street are one line. Business permit now also shows for logistics centers (the route already supported it). Suspension details and the live countdown are null-safe, and the countdown timer is cleaned up when the region is swapped.
- **Action dialogs:** suspend, deactivate, and activate/lift were restyled with entrance/exit transitions and busy states. Suspend text was copied from the activate dialog in both the mockup and the old code; it was rewritten, and the label now reads "Reason for suspension". The submitted fields (`reasons[]`, `additional_details`) are unchanged.
- **Motion:** a short page settle, modal fade and scale, dropdown fade, tab-pill slide with panel cross-fade, row reveal on refresh, and button press feedback. `prefers-reduced-motion` is respected.
- **Files:** `resources/css/admin/registrations.css` (new, `rg-` prefix, shared by both screens); `resources/views/admin/registrations/{index,show}.blade.php`; `registrations/partials/{registrations-table,applicant-details,reject-modal,confirmation-modal}.blade.php` (rewritten); `registrations/partials/{approve-modal,id-preview,id-lightbox}.blade.php` (new); `resources/views/admin/user-management/index.blade.php` and `user-management/partials/{users-table,profile-modal,suspend-modal,deactivate-modal,activate-modal,confirmation-modal}.blade.php`. `applicant-details` and `reject-modal` keep their contracts (`$user`, `$showExpr`, `$closeExpr`) because the Dashboard "Recent Registrations" modal includes them.
- `resources/css/admin/registrations.css` is registered in `vite.config.js`. All four pending-count icons (`pending-request-icon.svg`, `pending-seller-icon.svg`, `pending-buyer-icon.svg`, and `pending-logistics-icon.svg`) are present; the prior dashboard icons remain as fallbacks. User Management stat cards use the existing icons in a tinted circle. Run the normal Vite development or production asset process before acceptance.
- **Decisions that differ from the mockup:** primary button reads "Approve" (not "Approved"); "Logistics Center" is used instead of "Courier" because Admin manages logistics-center accounts; table headings read "User" and "Date Joined" on User Management; confirm buttons are solid colors; the search placeholder reads "Search by name or email".

### Known gaps (backend, not done)

- No rejection email exists. If the owner wants one, it needs a new mail class and a spec change.
- The mockup's Courier profile and Vehicle Information tab are not built. Riders are approved by their linked Logistics Center, `RegistrationController::approve` returns 403 for couriers, and `VerificationDocumentController::admin` has no courier documents (driver's license, OR/CR). Admin review of riders needs a decision on ownership first.
- User Management counts include pending and rejected accounts while the list excludes pending, so "Total Users" can exceed the visible rows. Counting only approved, suspended, and deactivated would match the table.
- Suspension is fixed at 7 days in `UserManagementController::suspend`; the mockup has no duration control.
- `admin.user-management.table` is no longer used by the screen. A lighter alternative to fetching the full index page is a table-plus-modals partial endpoint.
- Avatars show initials; stored `profile_picture` values are not displayed on these screens.
- Account audit events remain open.
- No tests, build, or browser walkthrough were run. Only the Alpine expressions were syntax-checked and Blade directives were checked for balance. Owner verification is pending, including the sticky decision bar, the in-place refresh while a modal is open, and the date picker in Safari.
