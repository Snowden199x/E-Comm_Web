## Placing an order in the Buyer app answered "Too Many Attempts"

The Buyer app could open checkout and review everything, but tapping the place-order action came back with Laravel's 429 *Too Many Attempts.* even on the first try, so no order was created.

The cause was the rate-limit keys in `routes/api.php`, not the checkout itself. Laravel's `ThrottleRequests` builds its cache key from the authenticated user only (`resolveRequestSignature()` returns the user id), so the buyer group's `throttle:120,1` — which counts **every** API call — and the stricter per-route limits inside that group were writing to and reading from one shared counter. Once ten buyer API calls had landed in a minute, `POST /api/v1/buyer/checkout` (`throttle:10,1`) saw a full bucket and refused the order. Ten calls is less than the app does before the buyer finishes typing: home (`/home`, `/cart`, `/notifications`), then checkout (`/checkout/preview`, `/locations`, `/checkout/shipping-quote`, one `/checkout/voucher-quote` per shop).

- `routes/api.php`: every throttle in the `auth:sanctum` + `EnsureApprovedBuyerToken` buyer group now passes a prefix, which Laravel prepends to the key and which therefore gives each limit its own bucket — `buyer` on the group (120/min), `buyer-checkout` (10/min), `buyer-shipping-quote` and `buyer-voucher-quote` (20/min each), `buyer-geo` (30/min, shared by search and reverse), `buyer-return` (10/min) and `buyer-chat` (20/min, shared by the two chat write endpoints). The limits themselves are unchanged; shipping quote and voucher quote deliberately still share one bucket because the checkout screen calls them for the same cart.
- `docs/features/buyer/mobile-api/spec.md`: new **Rate limits** section recording the per-buyer caps and why each throttle is prefixed.

Buyer-side effect: an ordinary minute of storefront, cart and checkout traffic no longer consumes the order-placement allowance, so `POST /checkout` only answers 429 after ten actual placement attempts in a minute.

### Verified

- `php artisan route:list --path=api/v1/buyer -v` shows `ThrottleRequests:10,1,buyer-checkout` on `api/v1/buyer/checkout` and the prefixed throttles on the other limited routes; `php -l` behaviour of the route file is unchanged (declarations only).
- Not verified: no order was placed and no HTTP request was replayed. The Buyer app, the web buyer pages, Rider and Transport Driver throttles were not exercised. Placing a real order in the app against a local server is the remaining check.

## Buyer Google sign-in rejected on the deployed build

The released Buyer app (`vendoph.buyer`) shows "Google could not verify this sign-in. Please try again." The message is the API's, not Google's: `POST https://vendo-ph.app/api/v1/buyer/google` returns 422 with exactly that `credential` error for a malformed token, so the request reaches `GoogleIdTokenVerifier` and is rejected there. A native OAuth misconfiguration would have failed earlier, with the app's own "Google does not recognise this app build" text and no request.

The verifier only rejects a well-formed Google token for two reasons: the audience (`aud`, always the shared web client) or the authorized party (`azp`, the Android package's own OAuth client) is missing from `services.google.allowed_client_ids`. The web client already works on production, so the failing entry is the Buyer package's client, `468116080938-v78hid0srlr7ke21rlpo1c3j5ot8jjk7`, which exists in the local configuration (three Android clients plus the web client) but was never added to the production environment.

No code changed: the new-account path is already implemented, and `BuyerGoogleAuthController` answers 202 with `registration_required`, `registration_token` and the verified email, which is what `login_screen.dart` uses to open the Buyer form with the address filled in, locked and already verified.

### Fix for the deployment

Add the Buyer Android client to the production environment and clear the cached configuration:

- `GOOGLE_ANDROID_CLIENT_ID` must contain the whole comma-separated list, ending with `468116080938-v78hid0srlr7ke21rlpo1c3j5ot8jjk7`.
- If `GOOGLE_ALLOWED_CLIENT_IDS` is set, it overrides the list above, so the same ID must be appended there instead.

### Verified

- `php artisan config:show services.google` locally lists `db4garqg...` (web) plus `ajc6emr9...`, `0uhu30n0...` and `v78hid0...` (Android) in `allowed_client_ids`.
- Production: `POST /api/v1/buyer/google` with a bogus credential returns 422 `Google could not verify this sign-in. Please try again.`; `/get-the-app` returns 302, so the deployed build includes this session's routes.
- Not verified: the production environment itself was not read, so the missing ID is inferred from the verifier's logic and the local/web-client evidence. The server log line `Google ID token rejected.` carries `authorized_party` and `audiences`, which confirm it directly.

## Registration uploads: 5MB cap, silent server rejection, half-saved seller

Reported from the buyer and seller registration forms: an ID photo or PDF uploaded fine but the form refused to submit, including a 10MB photo, and the page gave no usable reason. Three separate limits sat behind that one symptom.

- The validation rules capped every registration document at **5MB** (`max:5120`) while the form promised nothing, so a normal phone photo was rejected with "may not be greater than 5120 kilobytes" — and a body PHP itself refuses (`post_max_size`, `upload_max_filesize`) never reached validation at all, leaving a bare 413 or an empty request.
- An oversized body is discarded by PHP before Laravel sees it, so the only message the page could show was `data.message` or a generic failure. Nothing logged it, which is why `storage/logs/laravel.log` had no registration entry to inspect.
- `Seller\RegisteredUserController::store()` created the user and then stored the two documents with no transaction. A failed upload left a pending seller row behind, so the retry then failed on `unique:users,email`.

Changes:

- `app/Http/Controllers/Buyer/RegisteredBuyerController.php`, `Buyer/RegisteredUserController.php`, `Seller/RegisteredUserController.php`, `Logistics/Auth/RegisteredUserController.php`: document limit raised to **10MB** (`max:10240`) with explicit `max`, `mimes`, and `uploaded` messages, so a size failure says "10MB or smaller" and an interrupted upload says the file could not be uploaded instead of leaving a bare rule name.
- `Seller\RegisteredUserController::store()`: user, profile, categories, and both stored documents now run in one `DB::transaction`; stored files are deleted when it rolls back. A failed upload no longer burns the email address.
- `bootstrap/app.php`: `PostTooLargeException` answers JSON clients with a readable 413 instead of the framework page, and the status is named as the upload limit.
- `public/.user.ini` (new) and the `public/.htaccess` `mod_php` block: `upload_max_filesize 12M`, `post_max_size 16M`, `max_file_uploads 20`. PHP's stock 2M/8M is what turns a 10MB photo into a discarded request on a default host; nginx deployments still need the same values in `php.ini` or the FPM pool, since neither file is read there.
- `resources/views/buyer/auth/registration-scripts.blade.php` and `resources/views/seller/auth/register.blade.php`: 413 says the file is larger than the server accepts, 419 says the page expired and to refresh. Both forms now show the real cause instead of "Registration failed".
- `resources/views/buyer/auth/register.blade.php`, `resources/views/seller/auth/register.blade.php`: the format hint reads "JPEG, PNG, or PDF, up to 10MB each".
- `docs/features/buyer/customer-auth/spec.md`, `docs/features/seller/seller-auth/spec.md`: current-behavior lines record the 10MB cap and the single-transaction seller registration.

Verified: `php -l` on the four controllers and `bootstrap/app.php`; this machine's PHP reports `post_max_size 32M` / `upload_max_filesize 12M`, so a 10MB file fits locally. Not verified: no form was submitted and no server or test suite was run — the owner tests. A host that hard-caps uploads below 12MB will still reject the file; the message now says so.

## Google sign-in on the shared /login page

The owner pointed out that only `/logistics/login` appears to offer Google. It was a deliberate gap: `/login` is the shared Buyer+Seller page and the Google partial was wrapped in `@unless ($isUnified)`, because `POST /auth/google` required a `role` and that page cannot know the account type before the email is verified. Sellers sign in there, so they saw no button either.

- `resources/views/buyer/auth/login.blade.php`: the divider and Google button now render on the shared page too; it passes `role => null` there and keeps `'buyer'` on `/buyer/login`.
- `resources/views/auth/partials/google-signin.blade.php`: `role` is optional; `data-role` is emitted only when a page actually scopes it.
- `resources/js/auth/google-signin.js`: the posted body includes `role` only when the page sent one.
- `app/Http/Controllers/Auth/GoogleAuthController.php`: `role` is now nullable. Without it the server verifies the token, looks the email up, and signs the account in under its own role — Buyer to `buyer.dashboard`, Seller to `seller.dashboard` — after the same active/approval/profile checks. A Logistics, Rider, or Admin email is answered `409` with a message naming that account's own login page, so the shared page cannot become a second door into those portals. An email with no account is sent to `register.choose`, since there is no role yet to attach a Google registration proof to, and that signup needs the normal email OTP.
- Role-scoped pages are unchanged: `/buyer/login`, `/seller/login` and `/logistics/login` still send their role, and a token from another account type is still rejected with the existing "different account type" message.
- `docs/features/shared/google-auth/spec.md`: behavior, status, and source list updated.

Verified: `php -l` on the controller, `node --check` on the script, `php artisan view:cache` compiles the Blade, `npm run build` rebuilt `public/build` with the new script. Not verified: no Google token was exchanged and no browser click was made; the owner's OAuth configuration and a real sign-in on `/login` remain untested.
