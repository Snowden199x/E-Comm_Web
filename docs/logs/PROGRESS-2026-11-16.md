# Progress — 16 November 2026

## Placing an order in the Buyer app answered "Too Many Attempts"

The Buyer app could open checkout and review everything, but tapping the place-order action came back with Laravel's 429 *Too Many Attempts.* even on the first try, so no order was created.

The cause was the rate-limit keys in `routes/api.php`, not the checkout itself. Laravel's `ThrottleRequests` builds its cache key from the authenticated user only (`resolveRequestSignature()` returns the user id), so the buyer group's `throttle:120,1` — which counts **every** API call — and the stricter per-route limits inside that group were writing to and reading from one shared counter. Once ten buyer API calls had landed in a minute, `POST /api/v1/buyer/checkout` (`throttle:10,1`) saw a full bucket and refused the order. Ten calls is less than the app does before the buyer finishes typing: home (`/home`, `/cart`, `/notifications`), then checkout (`/checkout/preview`, `/locations`, `/checkout/shipping-quote`, one `/checkout/voucher-quote` per shop).

- `routes/api.php`: every throttle in the `auth:sanctum` + `EnsureApprovedBuyerToken` buyer group now passes a prefix, which Laravel prepends to the key and which therefore gives each limit its own bucket — `buyer` on the group (120/min), `buyer-checkout` (10/min), `buyer-shipping-quote` and `buyer-voucher-quote` (20/min each), `buyer-geo` (30/min, shared by search and reverse), `buyer-return` (10/min) and `buyer-chat` (20/min, shared by the two chat write endpoints). The limits themselves are unchanged; shipping quote and voucher quote deliberately still share one bucket because the checkout screen calls them for the same cart.
- `docs/features/buyer/mobile-api/spec.md`: new **Rate limits** section recording the per-buyer caps and why each throttle is prefixed.

Buyer-side effect: an ordinary minute of storefront, cart and checkout traffic no longer consumes the order-placement allowance, so `POST /checkout` only answers 429 after ten actual placement attempts in a minute.

### Verified

- `php artisan route:list --path=api/v1/buyer -v` shows `ThrottleRequests:10,1,buyer-checkout` on `api/v1/buyer/checkout` and the prefixed throttles on the other limited routes; `php -l` behaviour of the route file is unchanged (declarations only).
- Not verified: no order was placed and no HTTP request was replayed. The Buyer app, the web buyer pages, Rider and Transport Driver throttles were not exercised. Placing a real order in the app against a local server is the remaining check.

## Buyer notifications carry the order, so the app stops guessing the status

The Buyer app's notification card said **Order placed** for an order that had already been completed. The API sent only the title ("ORD-2026-0036: Completed") and the message, and the app derived a parcel status by matching words; *Completed* matched nothing, so it fell through to the "placed" default. The payload also gave the app no order to open.

- `app/Services/BuyerApiPresenter.php`: `notification()` now sends `order` = `{id, number, status, status_label}` (or null), resolved from the notification's `/buyer/orders/{id}` link and scoped to `buyer_id`, cached per user and path like the existing `product` lookup. `product`, `time_ago` and the rest of the payload are unchanged.
- `docs/features/buyer/mobile-api/spec.md`: the notifications bullet records `product` and `order`.

Practical effect: the app can label a card from the real status (Completed, Delivered, Cancelled, Returned, Delivery failed…) and open that order when the card is tapped.

### Verified

- `php -l` on the presenter: clean. Read-only check through `php artisan tinker` on the newest buyer order notification (`ORD-2026-0036: Completed`): `order` = `{id: 36, number: ORD-2026-0036, status: completed, status_label: Completed}`, `product` = Whey Protein with its image. No rows were written.
- Not verified: the app itself (separate repository) and the `order => null` path over HTTP for an announcement or a review notice.
