# Progress — 16 November 2026

## Placing an order in the Buyer app answered "Too Many Attempts"

The Buyer app could open checkout and review everything, but tapping the place-order action came back with Laravel's 429 *Too Many Attempts.* even on the first try, so no order was created.

The cause was the rate-limit keys in `routes/api.php`, not the checkout itself. Laravel's `ThrottleRequests` builds its cache key from the authenticated user only (`resolveRequestSignature()` returns the user id), so the buyer group's `throttle:120,1` — which counts **every** API call — and the stricter per-route limits inside that group were writing to and reading from one shared counter. Once ten buyer API calls had landed in a minute, `POST /api/v1/buyer/checkout` (`throttle:10,1`) saw a full bucket and refused the order. Ten calls is less than the app does before the buyer finishes typing: home (`/home`, `/cart`, `/notifications`), then checkout (`/checkout/preview`, `/locations`, `/checkout/shipping-quote`, one `/checkout/voucher-quote` per shop).

- `routes/api.php`: every throttle in the `auth:sanctum` + `EnsureApprovedBuyerToken` buyer group now passes a prefix, which Laravel prepends to the key and which therefore gives each limit its own bucket — `buyer` on the group (120/min), `buyer-checkout` (10/min), `buyer-shipping-quote` and `buyer-voucher-quote` (20/min each), `buyer-geo` (30/min, shared by search and reverse), `buyer-return` (10/min) and `buyer-chat` (20/min, shared by the two chat write endpoints). The limits themselves are unchanged; shipping quote and voucher quote deliberately still share one bucket because the checkout screen calls them for the same cart.
- `docs/features/buyer/mobile-api/spec.md`: new **Rate limits** section recording the per-buyer caps and why each throttle is prefixed.

Buyer-side effect: an ordinary minute of storefront, cart and checkout traffic no longer consumes the order-placement allowance, so `POST /checkout` only answers 429 after ten actual placement attempts in a minute.

### Verified

- `php artisan route:list --path=api/v1/buyer -v` shows `ThrottleRequests:10,1,buyer-checkout` on `api/v1/buyer/checkout` and the prefixed throttles on the other limited routes; `php -l` behaviour of the route file is unchanged (declarations only).
- Not verified: no order was placed and no HTTP request was replayed. The Buyer app, the web buyer pages, Rider and Transport Driver throttles were not exercised. Placing a real order in the app against a local server is the remaining check.

## Buyer notifications carry the order, so the app stops guessing the status

The Buyer app's notification card said **Order placed** for an order that had already been completed. The API sent only the title ("ORD-2026-0036: Completed") and the message, and the app derived a parcel status by matching words; *Completed* matched nothing, so it fell through to the "placed" default. The payload also gave the app no order to open.

- `app/Services/BuyerApiPresenter.php`: `notification()` now sends `order` = `{id, number, status, status_label}` (or null), resolved from the notification's `/buyer/orders/{id}` link and scoped to `buyer_id`, cached per user and path like the existing `product` lookup. `product`, `time_ago` and the rest of the payload are unchanged.
- `docs/features/buyer/mobile-api/spec.md`: the notifications bullet records `product` and `order`.

Practical effect: the app can label a card from the real status (Completed, Delivered, Cancelled, Returned, Delivery failed…) and open that order when the card is tapped.

### Verified

- `php -l` on the presenter: clean. Read-only check through `php artisan tinker` on the newest buyer order notification (`ORD-2026-0036: Completed`): `order` = `{id: 36, number: ORD-2026-0036, status: completed, status_label: Completed}`, `product` = Whey Protein with its image. No rows were written.
- Not verified: the app itself (separate repository) and the `order => null` path over HTTP for an announcement or a review notice.

## The shopper landing page's app card sent buyers to the Rider app

The hero card on `/` ("Vendo is on mobile" → **Get the app**) and its fixed QR, `public/assets/buyer/buyer-app-qr.png`, both carried the absolute URL `https://vendo-ph.app/get-the-app`. The only `get-the-app` route in the application lives at `GET /logistics/get-the-app` (`logistics.rider-app`, inside the `/logistics` prefix group) and redirects to `config('services.vendo.rider_app_url')`. The root path was not declared at all, so a shopper who scanned the QR got a 404 instead of the Buyer app, and a shopper who guessed the Rider path would have installed the wrong app.

- `routes/web.php`: new public `GET /get-the-app` (`buyer-app`, declared at the root next to `/login`) redirecting 302 to `config('services.vendo.buyer_app_url')`, mirroring the Rider route's shape and comment style.
- `config/services.php`: `vendo.buyer_app_url` defaults to `https://github.com/Snowden199x/E-Comm_Mobile/releases/latest/download/vendo-buyer.apk` and can be overridden with `BUYER_APP_DOWNLOAD_URL`, so the fixed QR stays valid across releases and a Google Play move is a config change.
- `resources/views/buyer/partials/hero.blade.php`: the card links to `route('buyer-app')` instead of a hardcoded absolute host, so it resolves on any host the site is served from. The QR image is unchanged and still decodes to `https://vendo-ph.app/get-the-app`.
- Docs: new `docs/features/buyer/app-download/spec.md` (surface, route, default target, override, Play migration, gaps) and an index entry in `docs/README.md`.

Practical effect: scanning the buyer QR or tapping the hero card now redirects to the Buyer APK release asset instead of a 404, and the two apps keep separate routes and config keys (`buyer-app` / `/get-the-app` vs `logistics.rider-app` / `/logistics/get-the-app`).

### Verified

- `php artisan route:list --path=get-the-app` lists both `GET|HEAD get-the-app … buyer-app` and `GET|HEAD logistics/get-the-app … logistics.rider-app`.
- `php artisan config:show services.vendo` reports `buyer_app_url` = the `vendo-buyer.apk` GitHub URL and the unchanged `rider_app_url`.
- `zbarimg` on `public/assets/buyer/buyer-app-qr.png` decodes to `https://vendo-ph.app/get-the-app`; the Rider QR still decodes to `https://vendo-ph.app/logistics/get-the-app`.
- Not verified: no HTTP request was made to `/get-the-app`, and the redirect was not followed, because no `vendo-buyer.apk` release asset exists yet — until one is published the redirect lands on a 404 at GitHub.

### Gaps

- The redirect is a bare 302 to GitHub, so an unpublished asset shows GitHub's 404 rather than an install page; a small `/get-the-app` page (version, size, SHA-256, install steps) is the next improvement, matching the Rider spec's note.
- The card's hidden copy still says "Scan to get the app, or tap to download it" on the QR image, which assumes the printed image matches the current release — true because the URL is a redirect, not a build artifact.

## Buyer Android OAuth client registered on the API

The owner created the Android OAuth client for the renamed package `vendoph.buyer` in Google Cloud project `468116080938`: `468116080938-v78hid0srlr7ke21rlpo1c3j5ot8jjk7` (Google's downloaded client JSON reports `"installed"`, i.e. no client secret — Android clients have none). Google's token verifier checks the token's `azp` (the calling package's own Android client) as well as its `aud` (the web client), so the ID has to be in the API's allow-list, not only in the Console.

- `.env`: appended the new ID to `GOOGLE_ANDROID_CLIENT_ID`, comma-separated with no spaces, and dropped the trailing comma the line had accumulated. The two older clients stay: `468116080938-ajc6emr9…` (the pre-rename `com.example.vendo_buyer` build) and `468116080938-0uhu30n0…` (Rider, `vendoph.rider`). No `.env` value is a secret here — Android client IDs are public.

### Verified

- `php artisan config:clear` then `php artisan config:show services.google` lists three `android_client_ids` and four `allowed_client_ids` (web + three Android), with no empty entry from the removed trailing comma.
- Not verified: no Google sign-in was attempted, so the Console package/SHA-1 binding itself is unconfirmed from this machine — the first real **Continue with Google** tap in a rebuilt Buyer app is the check.

### Gaps

- The old `com.example.vendo_buyer` client stays on purpose until no such build is in use; removing it from the Console would break Google sign-in on those installs.
