# Progress log: 2 November 2026

## Transport driver trips: scan counts in the payload

- `app/Http/Controllers/Api/TransportDriverApiController.php`: `tripPayload()` now includes `origin_scanned` and `destination_scanned` next to the manifest. Both are counted from `order_facility_stops` — the origin rows with `departed_at` and the destination rows with `arrived_at` for the trip's manifest parcels — which is the same evidence `TransportTripWorkflow` checks before it lets a trip depart or close. The driver app shows them as dispatch and receiving progress, so a progress bar can no longer be faked from order statuses.
- No route, migration or permission change: the fields ride on `GET /trips`, `POST /trips/{trip}/depart` and `POST /trips/{trip}/arrive`, which already sit inside the approved-driver group.
- A trip with no facility id or no manifest parcels reports `0` for both counts instead of failing.

**Verified:** `php -l app/Http/Controllers/Api/TransportDriverApiController.php` → no syntax errors.

**Not run:** no HTTP request against a seeded trip and no new test, so the counts have not been exercised against real `transport_trips` data yet. The mobile side that consumes them is logged in `E-Comm_Mobile/docs/logs/PROGRESS-2026-11-02.md`.

**Known gaps**

- The counts are computed with one extra query pair per trip on the list response (up to 50 trips). If the board grows, fold them into the eager load or a grouped aggregate.
- The payload still has no route distance.

## Station Hub: assign a driver and the hub they must reach

- `routes/logistics_portal.php`: the station group gained `GET/POST lgp.station.trips*` plus `PATCH lgp.station.trips.{cancel,depart,arrive}`. The three trip actions reuse the existing `PortalController` methods, which already derive their facility scope from the signed-in station, so a Station Hub may only cancel/depart its own trips and record arrival for trips sent to it.
- `app/Http/Controllers/Logistics/PortalController.php`: new `stationTrips()`, `stationTripDestinations()` and `storeStationTrip()`. The page lists trips where this Station Hub is the origin or the destination, the drivers linked to it that are free, the available vehicles of its Province Hub, and the parcels eligible per destination. Saving creates a `station_transfer` trip with this Station Hub as origin and the chosen hub as destination, attaches the parcels, and sets the driver and vehicle to `on_trip`. The driver must belong to this Station Hub, hold a licence valid on the departure date and have an approved account; all checks run inside the transaction.
- `resources/views/logistics/station/trips.blade.php` (new): Driver Assignments page with the assign form (destination hub, driver, vehicle, departure, expected arrival, parcel checklist), the trip table with status tabs, a trip dialog with manifest and journey, and cancel/depart/arrive actions.
- Parcel checklist: `stationTrips()` now sends the tracking number, order number, buyer, delivery address (barangay/municipality/province), sorted time and a `delivers_here` flag per eligible parcel, and the destination options carry the hub's municipality and province. The page lists the parcels whose delivery address is inside the chosen hub first, with a **Delivers in this hub** pill and a green edge, a **Select the N for {hub}** shortcut and a **Passes through** label for the rest, so the station can load the parcels that end their journey at that hub and still see the transfers. `addressIsInsideHub()` compares municipality (and province when both are known) by name.
- `resources/css/logistics/workspace.css`: `.lg-parcel-option` styles for that checklist (green edge for the matching parcels, checked state, fact row). `npm run build` was re-run so the compiled bundle carries the class.
- `config/logistics_nav.php`: Station Hub sidebar gained **Driver Assignments** in the Pickups and deliveries group, directly below Delivery Queue, where station staff look for delivery work.
- `resources/views/logistics/station/drivers.blade.php`: an **Assign trip** action for an available, unexpired driver, which opens the form with that driver chosen (`?driver={id}`); `stationDrivers()` passes the URL.
- Station copy that said only the Province Hub schedules trips was corrected on the Station Dashboard and the Outgoing Transfers page, which now link to the assignment page; Delivery Queue also carries an **Assign driver** header action.
- Fixed a latent bug in the Province Hub `storeTrip()`: it called `modelKeys()` on a base `Collection` (it should be `pluck('id')`), so creating a Province Hub trip threw `Method Illuminate\Support\Collection::modelKeys does not exist`. Both paths now attach ids with `pluck('id')->all()`.

**Verified:** `php -l` on the controller, routes and nav config; `php artisan route:list --path=logistics/portal/station/trips` shows the five routes; `php artisan view:cache` compiles every Blade template.

**Not verified:** no browser walkthrough and no seeded-data run, so the assign form and the driver app board have not been exercised end to end. Per the repository rules no automated tests were added or kept.

**Known gaps**

- The driver is not notified when a Station Hub assigns a trip; it appears on the next app refresh. Push notifications remain unimplemented.
- The page loads up to 60 trips with no paging, and the trip type stays `station_transfer`, so reports cannot tell a Station Hub assignment from a Province Hub transfer.
- The driver app cannot yet show who assigned the trip beyond the origin facility name.
