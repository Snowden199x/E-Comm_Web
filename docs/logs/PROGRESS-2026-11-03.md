# Progress log: 3 November 2026

## One identity document at registration: licence instead of licence + valid ID

- `app/Http/Controllers/Api/RiderRegistrationController.php`: `valid_id` is now `nullable` (still `image|mimes:jpeg,png,webp|max:5120`), because the Rider app submits the driver's licence as its identity document. The storing loop skips files that were not sent, and `courier_details.valid_id_path` falls back to the stored licence (`$stored['valid_id'] ?? $stored['drivers_license']`), so document review and `VerificationDocumentController` keep a working path for every rider. The `drivers_license` and `or_cr` uploads stay required.
- `app/Http/Controllers/Api/TransportDriverRegistrationController.php`: the same change for `POST /api/v1/transport-driver/register` — nullable `valid_id`, a `hasFile()` guard in the store loop, and `valid_id_path` falling back to `drivers_license_path`.
- Old app builds that still send `valid_id` are unaffected: the field is validated and stored exactly as before, it is just no longer mandatory.
- `app/Http/Controllers/Logistics/PortalController.php`: `driverCard()` gained `has_valid_id`, true only when the stored valid ID is a different file from the licence. Now that both paths usually point at the same upload, the Province Hub and Station Hub driver dialogs hide the duplicate **Valid ID** button instead of opening the licence twice (`resources/views/logistics/province/drivers.blade.php`, `resources/views/logistics/station/drivers.blade.php`). `resources/views/logistics/riders.blade.php` applies the same rule to the pending-rider document links.
- No migration, route, permission or storage-layout change: the fallback path is written into the existing columns inside the same directories (`private/rider-verification`, `private/transport-drivers`).
- Docs updated: `docs/features/courier/registration-api/spec.md` and `docs/design/logistics-hub-restructure-backend-spec.md`. The mobile side is logged in `E-Comm_Mobile/docs/logs/PROGRESS-2026-11-03.md`.

**Verified:** `php -l` on the two API controllers and `PortalController` → no syntax errors; `php artisan view:cache` compiles every Blade template; `flutter analyze` on `vendo_driver` → no issues, and on `vendo_rider` → the same 12 pre-existing warnings/info (login, register, home, profile, splash, shared widgets), none of them from this change.

**Not run:** no registration request was posted against the API and no test was added, so the optional-upload path and the licence fallback are compile-checked rather than exercised end to end.

**Known gaps**

- `valid_id_path` now holds a licence file for new riders and drivers; an older admin document notification that links "Valid ID" opens the licence image.
- The Buyer app still requires a valid ID, which is correct: buyers submit no other identity document.

## Transport driver: load scan endpoint for dispatch

- `POST /api/v1/transport-drivers/trips/{trip}/scan` (approved-driver group, `TransportDriverApiController@scan`): the driver sends a `tracking_number` and a UUID `scan_key`. The parcel must be on that trip's manifest and the trip must still be `scheduled`; ownership is checked the same way as `depart`/`arrive` (driver id plus company).
- `App\Services\TransportTripWorkflow::scanLoad()`: inside a transaction it locks the trip, the order and its origin `order_facility_stops` row, then records the scan as that row's `departed_at` — the same evidence `depart()` already requires — and writes a `facility_scan_events` row (`action = departure`) attributed to the driver plus a status note on the order. The order status is left alone: `depart()` still moves the whole manifest to `in_transit_to_hub`. A parcel whose origin stop already departed, or a reused `scan_key`, returns `duplicate: true` instead of an error, so a retried request is idempotent.
- `TransportDriverApiController::tripPayload()`: the manifest now carries `origin_scanned` / `destination_scanned` per parcel, and the top-level counts come from the same `scannedOrderIds()` helper. The driver app ticks the exact parcels it has scanned instead of assuming the first N are done. Field names, routes and payload keys the app already used are unchanged.

**Verified:** `php -l` clean on the controller, the workflow and `routes/api.php`; `php artisan route:list --path=transport-drivers` shows the new route next to `depart` and `arrive`.

**Not run:** no HTTP request against a seeded scheduled trip, so the transaction, the duplicate path and the 409 messages are not exercised yet. The mobile side is logged in `E-Comm_Mobile/docs/logs/PROGRESS-2026-11-03.md`.

**Known gaps**

- A driver scan needs an origin `order_facility_stops` row. A parcel without one is refused with a readable 409 rather than the stop being invented, so trips whose origin hub is not on the parcel route still cannot be scanned by the driver.
- The scan writes `departed_at` but not `arrived_at`/`sorted_at`; those stay the hub staff's own records.
- No rate limit per parcel beyond the route's `throttle:30,1` and the unique `scan_key`.

## Transport driver: one scan can load a container

- `POST /api/v1/transport-drivers/trips/{trip}/scan` now accepts `tracking_number` **or** `tracking_numbers` (1–100 strings, either one required) and records the whole list in one transaction. `TransportTripWorkflow::scanLoad()` takes the array and reports `recorded`, `duplicates`, `unknown` and `not_routed` separately, so one bad number on a container label does not fail the parcels that are really on the trip. Ownership checks and the scheduled-trip gate are unchanged.
- `facility_scan_events.scan_key` is unique per row, so a single-parcel scan still stores the app's `scan_key` while a multi-parcel scan stores a fresh `Str::uuid()` per parcel; idempotency comes from the origin stop's `departed_at`, which turns a repeated label into `duplicates` instead of a second write.
- `TransportDriverApiController::scan()` answers with `recorded`, `duplicates`, `unknown`, `not_routed`, `duplicate` and the message ("12 parcels scanned. 14 of 20 on board."), plus the trip payload with per-parcel flags, so the app can tick several parcels from one scan.

**Verified:** `php -l` clean on the controller and the workflow; `php artisan route:list --path=transport-drivers/trips` still shows the scan route.

**Not run:** no HTTP request against a seeded trip, so the multi-row transaction, the scan-key generation and the mixed label (some duplicates, some unknown) are not exercised yet.

**Known gaps**

- There is no container table: the label is only a list of tracking numbers, so the web has no container to search, print or reconcile against a trip.
- The label list is capped at 100 parcels per request.
- `unknown` and `not_routed` codes are reported but not logged anywhere beyond the response.
