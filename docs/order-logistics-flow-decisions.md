# Order and Logistics Flow Decisions

## Current status sequence and owners

Buyer checkout creates `placed` seller-specific orders. Seller can accept, prepare, and move an order to `ready_for_pickup`; seller cannot mark physical pickup. Readiness invokes `OrderRoutingService`, which selects an approved, active pickup Main Hub from seller location and a destination Main Hub from the structured buyer shipping location. Selection prefers an exact municipality match, then the unique nearest center in the same province using approximate municipality points. Missing or ambiguous matches stay unresolved. There is no admin dispatch action.

The origin center assigns an approved pickup rider linked to it. That rider's barcode/QR scan moves `ready_for_pickup → picked_up`, then an arrival scan moves `picked_up → at_sorting_center`; the center may also manually record arrival. When origin logistics sorts a cross-hub parcel, `LogisticsRoutePlanner` selects an active configured route plan for that exact origin/destination Main Hub pair. It picks the route with a virtual checkpoint municipality nearest the buyer's municipality, then uses approximate route length and configured priority to resolve close ties. The ordered plan and its first stop are stored on the order. If there is no valid plan, the order remains `sorted` with no route checkpoint assumed.

The route selection only names a planned path and next waypoint. It does not mean the parcel has arrived at that locality or prove a scan, truck movement, or custody transfer. After sorting a cross-hub parcel with a configured route, the origin Main Hub may assign/reassign an approved Truck Rider linked to that center. The Rider API exposes that assignment and planned route to the assigned Truck account only. Existing mobile API states `to_soc5` and `to_soc6` remain transitional legacy stages and do not confirm an SH5/SH6 arrival. The separate SH scanner app must confirm physical checkpoint arrivals/sorting and route advancement. The destination Main Hub confirms actual receipt (`at_destination_hub`) before assigning a delivery rider. Same-center parcels can be assigned from `sorted`.

The assigned destination rider scans `assigned_to_rider → out_for_delivery`, then scans after handover for `out_for_delivery → delivered`. The latter is the rider's report of delivery, not independent buyer receipt proof. Buyer receipt confirmation moves `delivered → completed`, after which product rating is available; the buyer's final progress label is **Rate Product**. `delivery_failed` and `returned` remain in `Order::STATUSES`, but exception routes are not built. Seller pre-pickup cancellation remains supported with stock restoration. Implemented scan transitions create scan and status events with center/city, and notify seller, buyer, and center owner. Manual hub transitions also notify seller and buyer with center/city context. Mobile scanner applications remain in separate repositories.

## Location data and limits

Checkout requires a selected province and city/municipality from the bundled PSGC snapshot and saves both codes and names on the order. The free-text address holds street/barangay detail; the server appends city and province. Older orders have only free-text addresses and cannot safely infer a destination hub. Use `php artisan orders:route-ready` after migrations to assign eligible existing ready orders; approving or reactivating a logistics center also retries unresolved ready orders.

The PSGC snapshot is a fixed reference, not proof of current administrative boundaries. Main Hub matching prefers an exact municipality; otherwise it ranks approved active centers in the same province using approximate representative municipality points. Ties, unmatched coordinates, or no eligible center remain unresolved. Straight-line points do not prove road/ferry links, capacity, service coverage, or travel time. A primary-center policy, reassignment, exceptions, consolidation, truck manifests, delivery proof, and refunds remain future work. The initial scan contract is documented in the [rider scan API](features/courier/scan-api/spec.md).

## Virtual SH locality checkpoints

Use **SH** for *SubHub*, with examples SH5, SH6, and SH3. An SH has a code and a named municipality/locality that represents the nearest known place for a buyer or seller area; it has no exact street address and is not a registered Vendo logistics center. For example, SH3 may be named **Pagsanjan** because Pagsanjan is the nearest named locality to a buyer in Luisiana, Laguna. The locality point helps describe and choose a configured route. It does not imply a particular warehouse or exact scan coordinate.

Each route plan connects an origin Main Hub to a destination Main Hub and stores an ordered sequence of SH localities. For example, Manila Main Hub → SH5 (Muntinlupa) → SH6 (Calamba) → Laguna Main Hub. A different plan may go through SH3 (Pagsanjan) for a buyer in a farther Laguna area. If a buyer's municipality is closest to SH6, a configured plan through SH6 can be chosen without forcing SH5. The origin seller area already determines the pickup Main Hub; SH localities can also be configured around the seller-side area where an intended route requires it.

Only active plans and active checkpoints for the exact Main Hub pair are eligible. Do not infer a route by searching all locality records. If no route is configured, keep the parcel sorted and show that no plan is available. DBeaver route setup is documented in the [virtual SH routing spec](features/logistics/subhub-routing/spec.md). Coordinates give municipality-level straight-line proximity only; they cannot establish a safe or operating road/ferry route.

The selected first checkpoint is only the next planned locality. The parcel must later be scanned by the separate mobile scanner app when it reaches the relevant route point/handoff. Each scan must authenticate an authorized scanner and record actual arrival separately from the next planned destination. The web Logistics Center portal must not advance SH arrival or pretend that the checkpoint is a staffed facility. Courier, rider, truck, and SH scanner interfaces are mobile-only; there is no web dashboard for them.

The earlier `logistics_sub_hubs`/`orders.next_sub_hub_id` migration is a physical-site draft. The current route planner uses `logistics_route_checkpoints`, `logistics_route_plans`, and `logistics_route_plan_stops`; any legacy rows are copied as locality labels, without their owner or address. Legacy `soc5`/`soc6` scan names do not confirm arrival at the new SH localities.

See [virtual SubHub route checkpoints](features/logistics/subhub-routing/spec.md), [truck and linehaul dispatch](features/logistics/company-truck-linehaul-dispatch/spec.md), [mobile rider API](features/courier/scan-api/spec.md), [seller shipments](features/seller/shipments/spec.md), and [schema](schema.md).

## Pickup request review (4 October 2026)

When a Seller marks an order `ready_for_pickup`, routing assigns an origin Main Hub and notifies its Logistics account. The center must verify the pending pickup request before assigning an approved pickup Rider. If the package is not ready, the center records a reason and returns the order to `preparing`; the Seller sees the reason and can mark it ready again after fixing the issue. This review is a Main Hub decision; it is not proof that the Rider physically collected the parcel. The Rider scan still records physical pickup.

A destination Main Hub may assign several eligible parcels in one delivery area to one approved Motorcycle/Van/L300 Rider in one locked transaction. Truck assignments remain the separate linehaul workflow. These web actions do not record physical SH arrival or sorting; those require the future scanner/mobile contracts.
