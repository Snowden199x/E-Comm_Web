# Google sign-in

**Status:** Server verification and Buyer/Seller/Logistics browser login implemented; Rider API exchange implemented. Owner OAuth configuration and acceptance verification pending.
**Updated:** 16 November 2026

## Behavior

Buyer, Seller, and Logistics login pages render the official Google Identity Services button in English, independent of browser/account locale. The browser posts Google's ID token to same-origin `POST /auth/google` using a relative URL so HTTPS deployments behind a proxy or tunnel do not accidentally generate an HTTP fetch URL. Laravel validates its signature with Google's cached JWKS, issuer, expiry, verified email, audience, and authorized party against configured client IDs. Invalid or unconfigured credentials are rejected. Rejection logs contain only a reason category and non-sensitive validation booleans; tokens, email addresses, and token claims are not logged. A matching existing account signs in only under its own role and after active/approval/profile checks; Logistics Company accounts redirect to the current `lgp.company` portal. A new identity receives a short-lived role-bound session proof and is redirected to that role's existing registration form. The Google email is prefilled and locked; all normal identity/profile/business documents, passwords, residence checks, and approval requirements remain.

The Buyer mobile app uses `POST /api/v1/buyer/google`. An existing approved active Buyer receives the normal buyer bearer token. A new identity receives `202` with a short-lived `registration_token` and the verified `email`, `given_name` and `family_name`; the app opens the Buyer registration form with that address filled in, read-only and marked **Verified with Google**, the names prefilled, and no emailed-code step, and posts the token as `google_registration_token`. The proof satisfies email verification only: identity photos, birthdate, address, password and Admin approval still apply.

The Rider mobile app uses `POST /api/v1/rider/google`. Existing approved active Rider accounts linked to an approved active Main Hub receive the normal seven-day rider bearer token. New identities receive a short-lived registration proof plus the verified claims. The app runs both roles from one login screen, so it first asks **Create an account** (Rider or Driver) and then opens the matching application form with that address filled in, read-only and marked **Verified with Google**; the Rider and Driver registration endpoints accept the same `google_registration_token`, and the proof satisfies email verification only. Rider applications remain pending for Logistics Center approval.

Google authentication does not create a Firebase project or use Firebase Auth/Firestore/Realtime Database. `firebase/php-jwt` is used only to verify JWT signatures and claims. Web clients render Google's official button. The Flutter Rider integration uses `google_sign_in` on Android/iOS; the plugin does not support Linux desktop.

## Configuration

Set `GOOGLE_WEB_CLIENT_ID` to the Google OAuth Web client ID used by GIS and by the mobile apps as their server client ID. `GOOGLE_ANDROID_CLIENT_ID` and `GOOGLE_IOS_CLIENT_ID` accept comma-separated lists, because every Android package registers its own OAuth client in that project (`com.example.vendo_buyer` and `vendoph.rider`). The mobile apps send the web client as `serverClientId`, so an Android token carries that web ID as `aud` and the package's own Android client as `azp`; the verifier accepts the token only when both are allowed, so registering the client in Google Cloud is not enough on its own. These IDs default into `GOOGLE_ALLOWED_CLIENT_IDS`, which still overrides with its own comma-separated list of every accepted ID.

Every client must live in one Google Cloud OAuth project: when the app's `serverClientId` is a web client from project A and its package plus signing certificate is registered under project B, Google rejects the request before the app sees a token (`DEVELOPER_ERROR`, shown by the plugin as `[28444] Developer console is not set up correctly`). Both apps sign their builds with the committed debug key `E-Comm_Mobile/android-keys/vendo-debug.keystore` (SHA-1 `DC:3B:DF:DA:36:47:2F:8C:4D:2A:46:6F:BB:F1:FF:E4:F5:62:8E:C9`), so each package needs one Android client with that fingerprint in the project that owns the web client — currently `468116080938`. The Rider release upload key's SHA-1 must be added there too once it signs a distributed build. iOS bundle/client ID plus reversed client URL scheme, and macOS bundle/client ID plus callback URL scheme, are registered in the same project. Do not commit client secrets. Public client IDs are not secrets, but must be registered accurately. Production website origin and authorized redirect/origin configuration must include `https://vendo-ph.app`.

## Source evidence and limitations

`app/Services/GoogleIdTokenVerifier.php`, `app/Http/Controllers/Auth/GoogleAuthController.php`, `app/Http/Controllers/Api/RiderGoogleAuthController.php`, `resources/js/auth/google-signin.js`, `resources/views/auth/partials/google-signin.blade.php`, and `vendo_rider/lib/features/auth/screens/login_screen.dart`. Google signing keys are cached for six hours and refreshed for an unknown key ID. Cache availability and correct OAuth client configuration are required. No database migration is required. Owner browser, Android/iOS, OAuth-console, and deployed-domain verification remain pending.
