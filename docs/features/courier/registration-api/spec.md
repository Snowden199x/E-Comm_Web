# Rider Registration API

**Status:** Backend and Rider mobile registration with server-verified email proofs implemented; owner verification pending
**Updated:** 28 September 2026

`GET /api/v1/rider/locations` exposes the bundled PSGC province/city snapshot. After selecting a city, `GET /api/v1/rider/locations/{cityCode}/barangays` returns the bundled barangay code/name choices for that city and returns 404 for an unknown city. `POST /api/v1/rider/register` accepts personal, vehicle, and address fields including `province_code`, `city_code`, and `barangay_code`, plus three image uploads (`valid_id`, `drivers_license`, `or_cr`). Supported `vehicle_type` values are `Motorcycle`, `Van`, `L300`, and `Truck`. These endpoints are public and rate limited. The server validates that the city belongs to the province and that the barangay belongs to the city; it also validates document MIME and size, email uniqueness, password confirmation, and the supplied fields. The client never selects a logistics-center ID.

Before submission, the mobile app verifies the email with a six-digit code sent by the web API, or receives a short-lived registration proof after the API verifies a Google ID token. The registration request must include one proof token bound server-side to the exact normalized email. A new Google account continues through the same Rider registration form; Google verification does not bypass residence, document, profile, matched-hub, or approval requirements. Successful registration sets `email_verified_at` and consumes the proof. OTP attempts and sending are rate limited; OTP values are stored hashed in cache.

The server applies the same routing rule used for seller-ready orders: select one approved, active logistics center in the same city; otherwise select one in the same province. If none or more than one qualifies at the applicable level, registration returns a validation error and creates no rider. This is service-area matching by names from the PSGC snapshot, not a physical-distance or capacity calculation.

Successful registration stores verification images on the private local disk and creates a `users` row with `role=courier`, `status=pending`, plus a `courier_details` row tied to the matched center, inside one database transaction. The matched center sees the application in Rider Management and alone can approve/reject it. The API returns the center name and pending status; it does not issue a bearer token. The login endpoint checks rider and center approval before issuing one.

The vehicle type is stored in the existing string column; adding Van and L300 requires no migration. Truck alone is eligible for Main Hub linehaul assignment; Motorcycle, Van, and L300 use the existing pickup and local-delivery assignment flow. The province/city catalog and grouped barangay snapshot are bundled under `resources/data/`, so rider registration needs no live PSGC mirror request. The source snapshot is fixed and may lag current administrative changes; see `resources/data/README.md`. Reviewer access to the private documents, reassignment when no unique center exists, and a dedicated approval audit record remain unimplemented. The owner performs acceptance testing; no tests or app walkthroughs were run by the agent.
