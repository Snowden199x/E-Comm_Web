# Rider Registration API

**Status:** Backend and Rider mobile registration with server-verified email proofs implemented; owner verification pending
**Reviewed:** 14 October 2026

> New applications match the Rider's PSGC municipality to an active Station Hub. A sole eligible station is automatic; overlapping companies require the Superuser's primary-station assignment. Residence address choices remain the full PSGC list; see [province network and stations](../../logistics/province-network-and-stations/spec.md).

`GET /api/v1/rider/locations` exposes the bundled PSGC province/city snapshot. After selecting a city, `GET /api/v1/rider/locations/{cityCode}/barangays` returns the bundled barangay code/name choices for that city and returns 404 for an unknown city. `POST /api/v1/rider/register` accepts personal, vehicle, and address fields including `province_code`, `city_code`, and `barangay_code`, plus three image uploads (`valid_id`, `drivers_license`, `or_cr`). Supported `vehicle_type` values are `Motorcycle`, `Van`, `L300`, and `Truck`. These endpoints are public and rate limited. The server validates that the city belongs to the province and that the barangay belongs to the city; it also validates document MIME and size, email uniqueness, password confirmation, and the supplied fields. The client never selects a logistics-center ID.

Before submission, the mobile app verifies the email with a six-digit code sent by the web API, or receives a short-lived registration proof after the API verifies a Google ID token. The registration request must include one proof token bound server-side to the exact normalized email. A new Google account continues through the same Rider registration form; Google verification does not bypass residence, document, profile, matched-hub, or approval requirements. Successful registration sets `email_verified_at` and consumes the proof. OTP attempts and sending are rate limited; OTP values are stored hashed in cache.

The server applies the same Station Hub lookup used for Seller-ready orders. If the Rider's municipality has no eligible station or overlapping companies have no primary assignment, registration returns a validation error and creates no Rider. This is configured municipality coverage, not physical-distance or capacity calculation.

Successful registration stores verification images on the private local disk and creates a `users` row with `role=courier`, `status=pending`, plus a `courier_details` row tied to the matched center and Station Hub, inside one database transaction. The matched Station Hub sees the application in Rider Management and reviews it. The API returns center and station names with pending status; it does not issue a bearer token. The login endpoint checks approval and active membership before issuing one.

The vehicle type is stored in the existing string column. Motorcycle, Van and L300 are eligible for Station pickup/delivery tasks. The legacy `Truck` Rider option remains accepted for mobile compatibility; new Company transport legs instead use the separate `transport_driver` role and Province Hub approval. The province/city catalog and grouped barangay snapshot are bundled under `resources/data/`, so registration needs no live PSGC mirror request. The snapshot may lag current administrative changes; see `resources/data/README.md`. Mobile Station-task integration and a dedicated approval audit record remain open. The owner performs acceptance testing; no tests or app walkthroughs were run by the agent.
