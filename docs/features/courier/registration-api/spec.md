# Rider Registration API

**Status:** Backend and Rider mobile registration with server-verified email proofs implemented; owner verification pending
**Reviewed:** 15 November 2026

> New applications match the Rider's PSGC municipality to an active Station Hub. A sole eligible station is automatic; overlapping companies require the Superuser's primary-station assignment. Residence address choices remain the full PSGC list; see [province network and stations](../../logistics/province-network-and-stations/spec.md).

`GET /api/v1/rider/locations` exposes the bundled PSGC province/city snapshot. After selecting a city, `GET /api/v1/rider/logistics-companies?province_code=&city_code=` lists every Logistics Company that exists and is open for business (approved, with an approved and active logistics-center account) as `{id, name, serves_municipality, station_hub}`. `station_hub` is the Station Hub that will review the application — `{id, name, municipality, province}` — or `null` when that Company has no Station Hub in the chosen municipality, in which case `serves_municipality` is `false`. The list is not narrowed by which Company happens to hold coverage, so an applicant always sees the full set of Companies. `GET /api/v1/rider/locations/{cityCode}/barangays` returns the bundled barangay code/name choices for that city and returns 404 for an unknown city. `POST /api/v1/rider/register` accepts personal, vehicle, and address fields including `province_code`, `city_code`, and `barangay_code`, plus two required image uploads (`drivers_license`, `or_cr`) and an optional legacy `valid_id` (the licence doubles as the identity document, so the current app does not send it; when it is absent the licence is stored as the valid ID path). Supported `vehicle_type` values are `Motorcycle`, `Van`, `L300`, and `Truck`. These endpoints are public and rate limited. The server validates that the city belongs to the province and that the barangay belongs to the city; it also validates document MIME and size, email uniqueness, password confirmation, and the supplied fields. The client never selects a logistics-center ID.

Before submission, the mobile app verifies the email with a six-digit code sent by the web API, or receives a short-lived registration proof after the API verifies a Google ID token. The registration request must include one proof token bound server-side to the exact normalized email. A new Google account continues through the same Rider registration form; Google verification does not bypass residence, document, profile, matched-hub, or approval requirements. Successful registration sets `email_verified_at` and consumes the proof. OTP attempts and sending are rate limited; OTP values are stored hashed in cache.

When the Rider chooses a company, `POST /api/v1/rider/register` carries its `logistics_company_id` (optional) and the server resolves that Company's Station Hub for the municipality: the Superuser's primary-station row when it belongs to the Company, otherwise the Company's single station there. A company id with no Station Hub in that municipality answers 422 on `logistics_company_id`, naming the company and the municipality. Without a company id the previous lookup is used. If the Rider's municipality has no eligible station, registration returns a validation error and creates no Rider. This is configured municipality coverage, not physical-distance or capacity calculation.

Successful registration stores verification images on the private local disk and creates a `users` row with `role=courier`, `status=pending`, plus a `courier_details` row tied to the matched center and Station Hub, inside one database transaction. The matched Station Hub sees the application in Rider Management and reviews it. The API returns the `logistics_company`, center and station names with pending status; it does not issue a bearer token. The login endpoint checks approval and active membership before issuing one.

The vehicle type is stored in the existing string column. Motorcycle, Van and L300 are eligible for Station pickup/delivery tasks. The legacy `Truck` Rider option remains accepted for mobile compatibility; new Company transport legs instead use the separate `transport_driver` role and Province Hub approval. The province/city catalog and grouped barangay snapshot are bundled under `resources/data/`, so registration needs no live PSGC mirror request. The snapshot may lag current administrative changes; see `resources/data/README.md`. Mobile Station-task integration and a dedicated approval audit record remain open. The owner performs acceptance testing; no tests or app walkthroughs were run by the agent.
