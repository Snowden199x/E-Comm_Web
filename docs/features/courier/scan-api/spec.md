# Assigned Rider Scan API

**Status:** Rider assignments, pickup/delivery scans, facility scans, delivery proof, task issue reports, push-token registration, and Transport Driver trip endpoints are connected to the mobile app; owner migrations and verification pending
**Updated:** 23 October 2026

The seller's 4 × 6 inch label encodes only `orders.tracking_number` in both Code 128 and QR. A code is an identifier, not an authorization credential. The separate Flutter Rider client authenticates the approved courier account, opens its dashboard after successful password or Google login, and submits only work assigned to that account. This web repository does not add a rider dashboard or camera interface.

## Contract

- `POST /api/v1/rider/login`: `email`, `password`, `device_name`; returns a seven-day bearer token with only `rider:scan` ability, rider identity (including the registered `vehicle_type`), and approved center. Rider registration accepts Motorcycle, Van, L300, and legacy Truck accounts. Invalid credentials and inactive/unapproved accounts share a generic error. Login is rate limited.
- `GET /api/v1/rider/assignments`: bearer token required. Returns at most 100 current pickup or delivery orders assigned to that rider and their approved center, plus a `summary` object with loaded, pickup, delivery, and linehaul counts for the returned page. The mobile dashboard displays those server values and the first assigned parcel; it refreshes on return from Parcels. For a local delivery assignment, `stop` includes the buyer address and nullable `latitude`/`longitude` from the order's optional checkout pin. Coordinates are returned only to that assigned Rider; older orders and Buyers who skip location permission have null coordinates. Linehaul records include planned route and Main Hub names but no seller/buyer contact, street address, or coordinates. The old pickup-rider inter-hub work at `sorted`, `to_soc5`, and `to_soc6` is returned only for legacy orders without real facility stops. For an authenticated Truck Rider only, it also returns linehaul orders explicitly assigned to that rider while the order remains in an eligible route stage. Motorcycle, Van, and L300 riders use the same local pickup/delivery assignment flow. Same-hub sorted parcels do not appear as inter-hub pickup work. No other riders' orders are returned. Since 11 November 2026 the list also includes approved return legs for that Rider's destination center: `assignment: return`, a `return` object (`status`, `label`, `reason`, `refund_cents`, `picked_up_at`, `delivered_to_seller_at`, plus `buyer` and `seller` names/phones/addresses), a `stop` that points at the Buyer while the request is `pending_pickup` and at the Seller once it is `picked_up`, and a `summary.return` count. Cash, delivery-proof and delivery-window fields stay null on a return row, and the parcel leaves the list after the handover.
- `POST /api/v1/rider/scans`: bearer token required. Body: `tracking_number`, `scan_type`, and a client-generated UUID `scan_key` retained for offline retries. Transitions: `pickup` (`ready_for_pickup → picked_up`); `origin_arrival` (`picked_up → at_sorting_center`); `soc5` (`sorted → to_soc5`); `soc6` (`to_soc5 → to_soc6`); `destination_hub` (`to_soc6 → in_transit_to_hub`); `out_for_delivery` (`assigned_to_rider → out_for_delivery`); `delivered` (`out_for_delivery → delivered`). The three inter-hub scans require a resolved destination different from origin and the same assigned pickup rider/approved origin center. The `delivered` scan requires the assigned approved delivery rider at the destination center. It records the rider's report that the parcel was handed over; it does not provide a signature, photo, GPS proof, or buyer confirmation. Buyer receipt confirmation remains a separate web action (`delivered → completed`). The response has order ID, tracking number, new status, center, server scan time, and `duplicate` flag. The same key for the same rider/type returns the original event without another status change or notification; a conflicting key or stale stage returns 409. Other riders/centers get 403.
- `POST /api/v1/rider/facility-scans`: approved Truck Rider token required. Body: `tracking_number`, `facility_id`, and a client-generated UUID `scan_key`; the server always derives the next operation (`auto`) from the order's stored route and scan history. It accepts only a linehaul order assigned to the authenticated Truck Rider and an active origin Main Hub or actual facility stop on that order. The facility ID selects a facility but does not grant access. The first Main Hub scan records origin departure; a station arrival scan records receipt and sorting together; an intermediate station's next scan records departure. Previous-stop departure and route order are enforced by `FacilityScanWorkflow`. It writes the facility scan and order status event, updates eligible order status, and notifies Seller, Buyer, and the facility network. Reusing the same UUID for the same rider, order, and facility is idempotent. This records the assigned Rider's scan report, not independent GPS proof, a truck manifest, or third-party custody confirmation.
- `POST /api/v1/rider/logout`: revokes the current bearer token.
- `POST /api/v1/rider/delivery-proofs` (new facility-routed orders only): bearer token required. Body: `tracking_number`, stable UUID `scan_key`, `recipient_name`, required JPG/JPEG/PNG/WebP `photo` up to 5 MB, and optional `notes`. The authenticated Rider must be assigned for final delivery at the approved destination Logistics Center; the parcel must be `out_for_delivery`, assigned to the Rider's destination Station, and already received/sorted there. The API stores the image on the private local disk, creates one proof row per order, and records the normal idempotent `delivered` scan in the same transaction. The mobile app asks for recipient name and camera photo when the assignment response marks proof as required, then submits this endpoint using its saved UUID for safe retries. A retried request with the same scan key and Rider returns the original result; another key is rejected. Buyer receipt confirmation is still separate.
- `POST /api/v1/rider/tasks/{task}/exceptions`: bearer token required. Body: `reason` (`damaged`, `recipient_unavailable`, `unsafe_location`, `vehicle_issue`, or `other`) and required `details`. The server verifies that the active task and station belong to the authenticated Rider and that the order is still assigned to them. It changes only the RiderTask to `failed`, records a same-status order timeline event, and notifies Station staff, Company, Seller, and Buyer. It does not claim the parcel returned to a facility or automatically change custody/order status. The failed task is visible in Station Task Assignment; staff must verify custody before assigning another Rider. Scans by the failed Rider are blocked.
- `POST /api/v1/transport-drivers/login`: `email`, `password`, and `device_name`; returns a seven-day token with only `transport-driver:trip`, driver and company labels. It accepts only approved active Transport Drivers with an active Province Hub/company and unexpired license.
- `GET /api/v1/transport-drivers/trips`: returns scheduled and in-transit trips assigned to the authenticated Driver, including origin/destination, vehicle and a manifest of order/tracking numbers and current status. It excludes Buyer/Seller contact and street addresses.
- `POST /api/v1/transport-drivers/trips/{trip}/depart` and `/arrive`: act only on a trip assigned to the authenticated Driver and owned by the Driver's active company. Depart delegates to the same locked web workflow and requires all origin manifest departure scans. Arrive requires destination facility scans for every manifest parcel before closing the trip. Station scans remain the proof of facility receipt; the app action alone does not claim a parcel arrived. `GET /api/v1/transport-drivers/earnings` returns this driver's accrued per-stop shipping shares. `POST /api/v1/transport-drivers/logout` revokes the token.
- **COD cash on delivery (28 October 2026):** `POST /api/v1/rider/delivery-proofs` also takes `cash_collected`, the cash handed over by the Buyer. It is required when the assignment shows `cash_collection_required: true` (orders placed after the COD change, `money_status = not_collected`) and must equal the order's `cod_amount` to the centavo; otherwise the request fails with 422 on `cash_collected` and nothing is saved (no proof, no scan, no status change). On success, in the same transaction, one `order_cod_collections` row is written (Rider, Station Hub, amount, the same `scan_key`) and `orders.money_status` becomes `collected_by_rider`. A retry with the same `scan_key` does not create a second collection. Orders created before cash tracking (null `money_status`) ignore the field. The mobile app must send it for new orders; an app that does not will not be able to complete deliveries for them.
- `GET /api/v1/rider/assignments` now also returns, for delivery assignments, `cash_to_collect` (the order's `cod_amount`, two decimals) and `cash_collection_required`.
- `GET /api/v1/rider/cash`: returns the authenticated Rider's `summary.cash_on_hand` and `parcels_on_hand` (collections whose order is still `collected_by_rider`, meaning the Station Hub has not yet confirmed receipt) and up to 100 recent collections with order number, amount, collected-at and money status. It excludes other Riders. This is a ledger view, not a payment. Station Hub receipt is implemented in the web portal (`StationCashController::receive`): it moves the orders to `remitted_to_station` (or `discrepancy`) and the amount then drops out of `cash_on_hand`.
- **Return-to-station scan (11 November 2026):** `POST /api/v1/rider/deliveries/{order}/return-scan` with `tracking_number` and a stable `scan_key` UUID, modelled like the other Rider scans. The order must carry that tracking number, belong to the Rider's approved center as its destination and be assigned to that Rider, and be `delivery_failed`. It writes one `order_scan_events` row (`scan_type = returned_to_station`, same from/to status) plus a status-event note naming the Station Hub, notifies the Buyer, Seller and hub, and leaves the order `delivery_failed` so the final attempt can be booked. A repeated `scan_key` returns the same result with `duplicate: true`; a key reused for another action or Rider is a 409. The response includes `delivery_attempts`, `max_attempts` and `attempts_remaining`. This is the physical return the earlier status note described; the Rider app calls it after a failed attempt.
- **Return pickup and handover (11 November 2026):** `POST /api/v1/rider/deliveries/{order}/return-pickup` and `POST /api/v1/rider/deliveries/{order}/return-handover`, same body as the other scans (`tracking_number`, UUID `scan_key`). Both need an order in `returned` with an approved return request. Pickup is limited to the assigned delivery Rider (`delivery_courier_id`); handover is limited to the Rider who collected it. Pickup writes `return_status = picked_up` plus `pickup_rider_id`/`picked_up_at`; handover writes `delivered_to_seller`. Each writes one `order_scan_events` row (`return_pickup` / `returned_to_seller`) and a status note, notifies the Buyer and Seller, and answers with `return_status`, `return_status_label` and the timestamps. A repeated `scan_key` returns the current state with `duplicate: true`; a failed pre-condition is a readable 409. The app can reuse the scanner screen; no new fields are required.
- `GET /api/v1/rider/earnings`: returns the authenticated Rider's accrued shipping shares (one per-parcel payment for orders placed after 28 October 2026, per-stop shares for older orders), hub-credit count, and recent completed-order allocations. It excludes other users and settlements in review, and it includes both `delivered` and `completed` orders, so an accrual stays visible after the Buyer confirms receipt. Amounts are accrued, not a completed cash/bank payout.

All protected routes require an actual Sanctum personal access token as well as approval, active account, and approved active center membership on every request. Scans lock the order row, write `order_scan_events` and `order_status_events`, and update the order in one transaction. The Order status observer creates seller and buyer notifications naming the relevant hub/city; the scan workflow also notifies the center owner. The order timeline exposes the scan note to the authorized buyer and seller. Scan timestamps and center are server verified. For facility-routed completion, a recipient name and private photo are required; this is not GPS or identity verification.

This is the existing mobile Rider API. Its transitional SOC-coded inter-hub scan values remain for historical routes and reject orders with actual facility stops. Logistics can scan using its authenticated browser modal, and an assigned Truck Rider can now scan the origin Main Hub and actual ordered stops in the Rider app; see [province network and stations](../../logistics/province-network-and-stations/spec.md). Preserve historical SOC/SH scan events. The separate E-Comm_MSA scanner client and `/api/v1/sh-scanner` API implement the previous virtual-checkpoint design and are paused. Truck assignments return the next server-derived `planned_route.scan_target`; the Rider app must show the action only when this target exists and submit its facility ID with the tracking number and stable UUID. Delivery assignments also include the final `dispatch_facility` when a station is the local pickup point. Truck manifests and independently verified custody remain unimplemented. Rider and Truck interfaces remain mobile-only.

The Rider facility-scan endpoint adds no migration of its own. It depends on the province facility schema from `2026_10_14_120000_create_logistics_facilities.php` and `2026_10_14_121000_create_order_facility_scans.php`. Delivery proof depends on `2026_10_23_200000_create_order_delivery_proofs.php`; the owner runs migrations. HTTPS is required on the deployed domain. The Rider client stores the token securely and persists stable scan keys before sending, reusing them after connection failure. Independent GPS/identity proof, token/device management UI, and broader offline reconciliation are not implemented. Physical SubHub scan actions use the separate [SH scanner API](../../logistics/sh-scanner-api/spec.md); do not treat current `soc5`/`soc6` scans as that implementation. New Company Transport Driver trip login, manifests, and departure/arrival do not yet have an app-facing mobile API contract; the web portal trip workflow remains separate. No tests, builds, or app walkthroughs were run by the agent per the owner's testing rule.

The [transitional SOC-coded stages and planned SH locality routes](../../logistics/subhub-routing/spec.md) remain for historical orders. Company Transport Driver trips use the real-facility manifest tables. A task issue pauses that assigned RiderTask and requires Station follow-up; it is not a facility exception and does not assert physical return. Shipping quotes and accrued allocations use real route facilities only. Rider destination coordinates come from an explicit Buyer checkout pin; no coordinates are fabricated or externally geocoded. The map shows points and a direct visual connector, not road routing or turn-by-turn directions. No payout is executed by these endpoints.

## 11 November 2026: already-scanned answer and bulk pickup

- A scan of work that is already recorded now returns **409** with `Already scanned: this parcel was recorded as "<scan_type>" on <date>`. A repeated `scan_key` still returns the original event with `duplicate: true`.
- `POST /api/v1/rider/pickups/bulk` accepts `items[]` of `{tracking_number, scan_key}` (1–50). It runs the same pickup transition per parcel, returns `{results, picked_up, failed}`, keeps going when one parcel fails, and is idempotent per scan key. The rider app does not yet have a multi-select screen; the endpoint is available for it.
