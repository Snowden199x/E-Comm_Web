# Assigned Rider Scan API

**Status:** Backend supports assigned pickup/delivery scans and authenticated Truck facility scans; owner verification pending
**Updated:** 14 October 2026

The seller's 4 × 6 inch label encodes only `orders.tracking_number` in both Code 128 and QR. A code is an identifier, not an authorization credential. The separate Flutter rider client authenticates the approved courier account, shows assigned work, and submits the decoded tracking number. This web repository does not add a rider dashboard or camera interface.

## Contract

- `POST /api/v1/rider/login`: `email`, `password`, `device_name`; returns a seven-day bearer token with only `rider:scan` ability, rider identity (including the registered `vehicle_type`), and approved center. Rider registration accepts Motorcycle or Truck. Invalid credentials and inactive/unapproved accounts share a generic error. Login is rate limited.
- `GET /api/v1/rider/assignments`: bearer token required. Returns at most 100 current pickup or delivery orders assigned to that rider and their approved center. The old pickup-rider inter-hub work at `sorted`, `to_soc5`, and `to_soc6` is returned only for legacy orders without real facility stops. For an authenticated Truck Rider only, it also returns linehaul orders explicitly assigned to that rider while the order remains in an eligible route stage. Motorcycle, Van, and L300 riders use the same local pickup/delivery assignment flow. Linehaul records include the planned route and Main Hub names but no seller/buyer address or phone. Same-hub sorted parcels do not appear as inter-hub pickup work. No other riders' orders are returned.
- `POST /api/v1/rider/scans`: bearer token required. Body: `tracking_number`, `scan_type`, and a client-generated UUID `scan_key` retained for offline retries. Transitions: `pickup` (`ready_for_pickup → picked_up`); `origin_arrival` (`picked_up → at_sorting_center`); `soc5` (`sorted → to_soc5`); `soc6` (`to_soc5 → to_soc6`); `destination_hub` (`to_soc6 → in_transit_to_hub`); `out_for_delivery` (`assigned_to_rider → out_for_delivery`); `delivered` (`out_for_delivery → delivered`). The three inter-hub scans require a resolved destination different from origin and the same assigned pickup rider/approved origin center. The `delivered` scan requires the assigned approved delivery rider at the destination center. It records the rider's report that the parcel was handed over; it does not provide a signature, photo, GPS proof, or buyer confirmation. Buyer receipt confirmation remains a separate web action (`delivered → completed`). The response has order ID, tracking number, new status, center, server scan time, and `duplicate` flag. The same key for the same rider/type returns the original event without another status change or notification; a conflicting key or stale stage returns 409. Other riders/centers get 403.
- `POST /api/v1/rider/facility-scans`: approved Truck Rider token required. Body: `tracking_number`, `facility_id`, and a client-generated UUID `scan_key`; the server always derives the next operation (`auto`) from the order's stored route and scan history. It accepts only a linehaul order assigned to the authenticated Truck Rider and an active origin Main Hub or actual facility stop on that order. The facility ID selects a facility but does not grant access. The first Main Hub scan records origin departure; a station arrival scan records receipt and sorting together; an intermediate station's next scan records departure. Previous-stop departure and route order are enforced by `FacilityScanWorkflow`. It writes the facility scan and order status event, updates eligible order status, and notifies Seller, Buyer, and the facility network. Reusing the same UUID for the same rider, order, and facility is idempotent. This records the assigned Rider's scan report, not independent GPS proof, a truck manifest, or third-party custody confirmation.
- `POST /api/v1/rider/logout`: revokes the current bearer token.

All protected routes require an actual Sanctum personal access token as well as approval, active account, and approved active center membership on every request. Scans lock the order row, write `order_scan_events` and `order_status_events`, and update the order in one transaction. The Order status observer creates seller and buyer notifications naming the relevant hub/city; the scan workflow also notifies the center owner. The order timeline exposes the scan note to the authorized buyer and seller. The timestamp and center are server verified; no GPS coordinate or delivery proof is asserted.

This is the existing mobile Rider API. Its transitional SOC-coded inter-hub scan values remain for historical routes and reject orders with actual facility stops. Logistics can scan using its authenticated browser modal, and an assigned Truck Rider can now scan the origin Main Hub and actual ordered stops in the Rider app; see [province network and stations](../../logistics/province-network-and-stations/spec.md). Preserve historical SOC/SH scan events. The separate E-Comm_MSA scanner client and `/api/v1/sh-scanner` API implement the previous virtual-checkpoint design and are paused. Truck assignments return the next server-derived `planned_route.scan_target`; the Rider app must show the action only when this target exists and submit its facility ID with the tracking number and stable UUID. Delivery assignments also include the final `dispatch_facility` when a station is the local pickup point. Truck manifests and independently verified custody remain unimplemented. Rider and Truck interfaces remain mobile-only.

The Rider facility-scan endpoint adds no migration of its own. It depends on the province facility schema from `2026_10_14_120000_create_logistics_facilities.php` and `2026_10_14_121000_create_order_facility_scans.php`, which must be applied before these assignments and scans work. Earlier additive migrations create `personal_access_tokens` and `order_scan_events`; the owner runs migrations. HTTPS is required on the deployed domain. The Rider client stores the token securely, shows assigned work only, persists a stable scan key before sending, and reuses it after connection failure. Failed attempts, independent proof of delivery, token/device management UI, and broader offline reconciliation are later work. Physical SubHub scan actions use the separate [SH scanner API](../../logistics/sh-scanner-api/spec.md); do not treat the current `soc5`/`soc6` scans as that implementation. No tests or walkthroughs were run by the agent per the owner's testing rule.

The [transitional SOC-coded stages and planned SH locality routes](../../logistics/subhub-routing/spec.md) use the origin pickup rider for the current inter-hub scan values. A separate `linehaul_rider_id` stores the assigned Truck Rider for the planned route. The owner must run additive migration `2026_09_28_200000_add_linehaul_rider_to_orders.php`. Manifests, actual checkpoint scans, and custody remain unrepresented until the separate scanner API is defined.
