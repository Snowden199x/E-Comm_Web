# Admin Delivery Fees and Cash Remittances

**Status:** Web workflow written in code; migrations and owner verification pending. Part of the [COD cash and delivery fee design](../../../design/cod-cash-and-delivery-fee-distribution.md).

**Delivery Fees** (`GET admin/delivery-fees`, `PUT admin/delivery-fees`, `admin.delivery-fees.*`, Finance group in the Admin sidebar) edits the single `delivery_fee_settings` row: the **delivery fee commission %** (Vendo's share of the delivery fee after the Rider's fixed pay) and the **seller commission %** (Vendo's share of the item price). Both are 0 to 100 with two decimals. Only a super admin can save; other Admins see the values read-only. The row records `updated_by`, and the page shows who last changed it and when. A live preview applies the typed rates to a ₱100 fee with ₱10 Rider pay and to a ₱500 item. Each order saves the rates in force when it is placed, so changes apply to new orders only. No admin action log entry is written because `admin_action_logs` requires a target user.

The same page shows delivery commission earned (all time and this month), the number of parcels split, and a paginated table of distributions: one row per delivered parcel whose order carries saved rates, with delivery fee, Rider, Vendo, Logistics, the rates used, settlement date and a "Needs review" tag for route mismatches. Orders from before saved rates existed use the earlier per-stop rule and are not listed.

**Delivery Fees page redesign (31 October 2026).** The page uses the admin design tokens. Three cards (earned, this month, parcels split), a rates form with a preview beside it, and the distributions table. The "Seller commission now" card was removed because the form shows the same value. The form validates as you type: field errors say the fix ("Enter a rate from 0 to 100.", "Use at most 2 decimals, like 7.25."), and **Save rates** stays disabled until a rate changes and is valid. The footer lists what will change (for example "Seller commission 10% → 12%") and **Discard changes** restores the saved rates. Admins who are not super admins see the inputs disabled with a note. The server accepts at most 2 decimals instead of rounding silently and returns the same short messages. The distributions table pages in place with a skeleton, an empty state and an error with **Retry**, so typed rates are not lost when paging.

**Cash Remittances page redesign (31 October 2026).** The page uses the admin design tokens. Three status cards (Awaiting confirmation, Open discrepancies, Confirmed, each with its amount and batch count) also filter the table; selecting the active card clears it. Search finds a batch by reference or Company name. The table pages in place with a skeleton, empty states (no batches, no match) and an error with **Retry**. Rows with a pending batch show **Confirm receipt** and rows with a discrepancy show **Resolve**; both open one dialog instead of expanding the row. In the dialog the amount starts at the expected amount and says what happens: a match credits the Sellers, a difference holds the batch, needs a note and changes the button to **Record discrepancy**. Field errors say the fix, and a failed save reopens the dialog with what was typed. A batch another admin already handled (409) now shows a message on the page instead of an error screen. The received amount accepts at most 2 decimals. Confirmed rows show who confirmed and when, and resolved rows also show the note. The "Confirmed batches" card was removed; its count is on the Confirmed card.

**Cash Remittances** (`GET admin/cash-remittances`, `POST .../{remittance}/receive`, `PATCH .../{remittance}/resolve`, `admin.remittances.*`) lists `company_to_vendo` batches sent by Logistics Companies, pending first, with Company, parcels, expected and received amounts and status. Confirming a batch takes the amount received. A match sets the batch `received` and moves its orders to `credited_to_seller` (the cash-chain state; Seller earnings themselves are already credited on delivery); a difference requires a note and holds the orders in `discrepancy` until an Admin resolves it with a note, after which they move to the same state. The shared `CashRemittanceService` performs both steps under row locks and a batch can be confirmed only once. Admin accounts are `users` rows (guard `admin`), so the confirmer is stored in `verified_by` and `resolved_by`. Nothing here moves real money.

The existing Admin Commission and Reports pages now calculate commission per order from each order's saved seller rate (the fixed 10% for older orders), so a rate change never alters past commissions; `CommissionSetting::currentRate()` returns the current setting and is used for display only. The Seller side is the [Seller earnings spec](../../seller/earnings/spec.md).
