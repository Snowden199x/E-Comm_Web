# Data Schema Overview

This overview is derived from Eloquent models and migrations, not a replacement for the migrations. Field-level details should be confirmed from `database/migrations/` before changing the schema.

## Identity and profiles

- `users`: credentials, role, registration/account states, contact data, suspension/rejection metadata, profile picture, and archival fields.
- `buyer_details`, `seller_details`, `courier_details`, `logistics_centers`: one-to-one role profile records. Courier detail optionally belongs to a logistics center.
- `buyer_saved_items` stores unique Buyer/product pairs; `buyer_settings` stores one row per Buyer for text size, reduced motion, and notification sound. Both are added by `2026_10_07_100000_create_buyer_saved_items_and_settings.php` and require owner migration.
- `categories` is hierarchical through nullable `parent_id`; `seller_categories` links sellers to selected categories.
- `otp_verifications` stores buyer registration OTP records. Seller and logistics-center OTP verification currently uses cache keys instead.

## Logistics province network and facilities

Migration `2026_10_14_120000_create_logistics_facilities.php` is the legacy center-owned facility baseline; its province coverage column is no longer exclusive after the 23 October hierarchy migration. New migration `2026_10_23_130000_create_logistics_network_portals.php` links each existing Logistics Center to a Company and backfills facility company/parent IDs, changes legacy facility kinds to `province_hub`/`station_hub`, and removes the unique coverage constraint. Existing user, center, Rider, order, and scan records remain. A sole active station is selected automatically; if several companies cover a municipality, `primary_logistics_coverage` selects the Superuser-approved Station Hub.

Migration `2026_10_14_121000_create_order_facility_scans.php` adds ordered `order_facility_stops` with arrival/sort/departure timestamps and `facility_scan_events` with a globally unique retry key and one accepted action per parcel/facility. New sorts choose actual facility IDs, placing the destination Main Hub between origin and destination stations on cross-province routes. Old checkpoint and SH scanner tables remain historical virtual-checkpoint data; map an old checkpoint to a real facility only after operator confirmation. See [province network and stations](features/logistics/province-network-and-stations/spec.md).

## Commerce

- `products` belongs to a seller and optionally to a category; product images, warnings, and violations are separate records. Product approval state is stored on the product.
- `cart_items` belongs to a buyer and a product; optional variation/color/size fields are carried to order items.
- `orders` belongs to buyer and seller, optionally references a courier and a delivery Logistics Company, and stores gross product subtotal (`total_amount`), nullable `buyer_note`, Seller `voucher_code`/`voucher_discount` snapshots, shipping fee, payment mode, shipping address, and workflow status. Buyer payable total is subtotal minus voucher discount plus shipping. One buyer checkout can create separate orders for each seller.
- `order_items` snapshots product reference, quantity, selected variation, and price.
- `order_status_events` records status changes, actor, optional note, and event time; it is the basis for the order timeline.
- `orders.logistics_center_id` is the origin center; `destination_logistics_center_id` is the destination hub. `courier_id` and `delivery_courier_id` hold pickup and delivery riders; `linehaul_rider_id` holds the origin hub's assigned Truck Rider for a configured cross-hub route. Structured shipping province/city codes and names are snapshotted at checkout; legacy rows remain null. `order_logistics_assignments` records pickup, linehaul, and delivery rider assignments; status transitions remain in `order_status_events`. Additive migration `2026_09_28_200000_add_linehaul_rider_to_orders.php` adds the nullable FK and status lookup index; owner runs it.
- `buyer_details.latitude`/`longitude` store one optional delivery map pin for the Buyer's registered address, `seller_details.latitude`/`longitude` store the Seller shop pin, and `logistics_centers.latitude`/`longitude` store the Logistics company address pin. `buyer_details.preferred_delivery_company_id` stores an optional preferred Logistics Company. Migrations `2026_10_29_120000_add_delivery_map_and_preference_to_buyer_details.php` and `2026_10_29_130000_add_address_coordinates_to_seller_and_logistics_details.php` add them; the owner must run them.
- `orders.delivery_company_id` is the Logistics Company the Buyer chose for that order's delivery. It is nullable, so older orders keep the previous address-derived routing. Migration `2026_10_29_121000_add_delivery_company_to_orders.php` adds the FK and a company/status index; the owner must run it.
- `orders.shipping_latitude` and `shipping_longitude` optionally store a Buyer-selected device location or map pin for that delivery. Migration `2026_10_23_230000_add_shipping_coordinates_to_orders.php` adds nullable decimal coordinates. The Rider assignment API returns them only to the assigned local delivery Rider; older orders and orders without a pin remain null.
- Legacy `logistics_route_checkpoints` stores a virtual SH code and nearby locality name (for example SH3 / Pagsanjan), with municipality-level representative codes/coordinates and an inactive-by-default flag. It has no Logistics Center owner or street address. The route migration inserts inactive examples SH5/Muntinlupa, SH6/Calamba, and SH3/Pagsanjan. Legacy `logistics_route_plans` connects origin and destination Main Hubs; `logistics_route_plan_stops` stores ordered virtual checkpoint IDs. `orders.route_plan_id`, `route_step`, and `next_route_checkpoint_id` save a selected plan and next planned locality; they do not mean the parcel arrived or custody changed. The earlier `logistics_sub_hubs` and `orders.next_sub_hub_id` physical-site draft may remain for migration compatibility but are no longer used by current application code. Preserve all these rows during future facility migration.
- Legacy `sh_scanner_stations` belongs to one Logistics Main Hub and one virtual SH checkpoint. It holds station name, hashed five-minute pairing code, hashed expiring device token, pairing time, and revocation time; no operator public account is created. `sh_checkpoint_scan_events` records the accepted station/order/checkpoint/route plan/step and unique scan UUID. These records are historical legacy data, not the agreed future browser-camera/facility workflow. Migration `2026_10_12_130000_create_sh_scanner_stations_and_events.php` must not be dropped or repurposed destructively.
- `personal_access_tokens` holds expiring Sanctum rider bearer tokens. `order_scan_events` records the assigned rider, verified center, scan type, from/to statuses, unique per-order retry UUID, and server time. Both tables use additive 26 September migrations that the owner must run.

## Platform operations

- `notifications` may be user-targeted or platform-level. `announcements` support publication/audience/scheduling; `platform_policies` store policy content/versioning.
- `conversations`, `messages`, and `message_attachments` support messaging and optional complaint linkage. Case-linked conversations now hold private Buyer/Seller and Admin text threads; ordinary support threads have `complaint_id = null`. Conversations can be open/closed.
- `complaints`, `complaint_evidences`, `complaint_activities` represent dispute intake, attachments, and status history.
- `commission_settings` retains a legacy rate row, but `CommissionSetting::currentRate()` now always returns a fixed 10.00%; Admin product commission screens calculate from gross order items. `categories.commission_rate` also exists but is not used. There is no immutable Admin rate snapshot. Shipping quote and delivered-order Rider/Driver accrual tables are described in the later migration below; they do not implement payouts.
- `seller_category_requests` and `seller_category_request_categories` store Seller category applications, private permit paths, Admin decisions and reviewer IDs. Approved requests attach categories through the existing `seller_categories` pivot.
- `seller_vouchers`, `seller_voucher_products`, `seller_voucher_categories`, and `seller_voucher_redemptions` store Seller-scoped offers, applicability, usage limits, and one redemption per order. Retiring a voucher sets `deleted_at` instead of deleting historical redemptions; cancellation sets `voided_at` and releases `used_count`. The 13 October migration adds first-activation and expiration-notification timestamps plus `seller_voucher_notification_recipients`, uniquely keyed by voucher and Buyer with a link to the generated notification.
- `product_warnings` and `product_violations` record compliance actions. `admin_login_sessions` records admin login/device/session information.

## Important integrity notes

- Current checkout decrements product stock when placing an order, inside a transaction with locked product rows.
- Seller decline restores reserved stock under a transaction. Any additional cancel/refund path must be idempotent and audited to prevent duplicate restoration.
- The order workflow migration changes status from the original limited enum to a wider string to accommodate ERP stages. Validate all status writes against `Order::STATUSES`.
- Foreign-key cascade/null behavior is defined in migration files; inspect it before deleting or archiving records.

## Seller operations additions (24 September 2026)

- `inventory_movements`: product, nullable actor/order references, type, signed quantity, before/after stock, reason, unique optional request key and timestamps. Opening stock/restock/checkout/cancellation writes are transactional. Legacy balances are preserved; historical movements are not fabricated.
- `orders`: unique stable `tracking_number`, nullable carrier name/reference and ETA range, `shipping_fee` default zero for legacy/default records. New checkout orders store the server quote, stop count, and route snapshot. Legacy references are backfilled by migration; new references are generated on order creation. ERP order status remains the only fulfillment status source.

## 4 October 2026 additions (pending owner migration)

- `product_sequences` holds a locked annual counter for new `PRD-YYYY-NNNN` codes; existing ULID codes are retained. `products.status` adds `draft`, and product rows add condition, video path, packed weight/size, fragile flag, has-variations flag and optional compare-at price.
- `product_attribute_values`, `product_specifications`, `product_variation_types`, `product_variation_options`, and `product_variants` store Seller listing details and purchasable options. Category field definitions remain in `config/product-attributes.php`; each variant stores its selected type/value map as JSON.
- `cart_items.product_variant_id`, `order_items.product_variant_id` and `inventory_movements.product_variant_id` tie selection, purchase and stock movement to the selected variant. Product aggregate stock equals the sum of variant stocks for variant products.
- `orders.pickup_request_status`, `pickup_decline_reason` and `pickup_verified_at` record Main Hub review of a Seller pickup request. A decline returns the order to `preparing` and lets the Seller mark it ready again.
- `admin_action_logs` records actor Admin ID, target user ID, action, reason and timestamps for registration/account actions. These tables/columns are added by three new `2026_10_04_*` migrations.

## 23 October 2026 Logistics hierarchy additions (owner migration required)

- `logistics_companies` links each existing `logistics_centers` account to a Company record. Migration `2026_10_23_130000_create_logistics_network_portals.php` backfills these from existing rows and remaps legacy `main_hub` / `station` facility kinds to `province_hub` / `station_hub`, retaining facility records.
- `logistics_facilities` gains company/parent links, province and municipality routing keys, coordinates, and company/parent indexes. The old unique province-coverage index is removed so multiple companies can cover one province.
- `facility_staff` binds Province Hub and Station Hub manager users to one facility. `courier_details.station_hub_id` and `rider_service_areas` establish station-level Rider membership and service barangays. `rider_tasks` stores station-scoped pickup/delivery assignments.
- `transport_driver_details`, `company_vehicles`, `transport_trips`, and `transport_trip_orders` represent Province Hub Drivers, company vehicles, scheduled legs, and parcel membership. `LogisticsCompanyVehicle` and `LogisticsTransportTrip` explicitly map to the migration tables `company_vehicles` and `transport_trips`. Driver profile columns are extended by `2026_10_23_160000`. `orders` gains origin/destination Station/Province Hub references, route type, and buyer barangay fields.
- Migration `2026_10_23_220000_add_shipping_quotes_and_earnings.php` adds `orders.shipping_hub_count` and the JSON `shipping_route_snapshot`, plus one `order_shipping_settlements` row per delivered facility-routed order and per-stop `order_shipping_earning_lines`. The quote is ₱45 for up to two route facilities, then ₱10 for each extra facility. Rider/Driver lines accrue ₱10 per completed stop; unallocated value remains in the Logistics remainder. These are accounting records only, not payout execution. The owner must run the migration.
- `primary_logistics_coverage` stores the Superuser's chosen Station Hub for an overlapping PSGC municipality. `manual_logistics_handoffs` records cross-company sending and receiving custody, and `logistics_threads` / `logistics_thread_messages` store Company-to-facility conversations. These are added by `2026_10_23_150000`, `170000` and `180000` migrations; all are additive and owner migration is pending.
- Migration `2026_10_23_190000_add_logistics_operations_followups.php` adds ETA to `transport_trips`, `cross_company_manifests` for grouped cross-company handoffs and Driver/vehicle assignment, `manual_logistics_handoffs.manifest_id`, and `logistics_parcel_exceptions` with facility, reason, resolution, and actor fields.
- Migration `2026_10_23_200000_create_order_delivery_proofs.php` adds one `order_delivery_proofs` record per order, with Rider, Station, idempotency key, recipient name, private photo path, notes, and captured timestamp. Proof images live on Laravel's private `local` disk, not `public/storage`.
- Migration `2026_10_23_210000_create_logistics_account_change_requests.php` adds `logistics_email_changes` (one pending request per user and unique reserved new email) and `logistics_document_requests` for private ID/business-permit replacements and Admin review. The Company account's active document path changes only on approval.

## 28 October 2026 COD cash and delivery fee foundation (owner migration required)

Additive migrations `2026_10_28_100000_add_cod_and_delivery_fee_settings.php` and `2026_10_28_110000_create_cod_cash_remittance_tables.php`. Checkout writes the settings and snapshots, delivery writes the collection, and the Station → Province → Company → Vendo cash pages write the remittances and items (see the [COD cash and delivery fee design](design/cod-cash-and-delivery-fee-distribution.md) and the [29 October pull review](design/2026-10-29-cod-cash-pull-review.md)).

- `delivery_fee_settings`: one row of Vendo Admin rates, `vendo_delivery_commission_rate` (default 0, so Vendo takes no delivery fee share until set) and `seller_commission_rate` (default 10, matching the current fixed rate), with `updated_by`. The migration inserts the default row. `CommissionSetting::currentRate()` now returns `seller_commission_rate` for display; per-order commission and reports read each order's saved `seller_commission_rate` (10% when null).
- `logistics_companies.rider_pay_per_parcel`: fixed pay per delivered parcel set by each Company, default 10.00 to match the current ₱10 credit.
- `orders.cod_amount`, `money_status`, `rider_pay_rate`, `vendo_delivery_commission_rate`, `seller_commission_rate`: the cash the Rider must collect, the separate money status chain (`Order::MONEY_STATUSES`), and the rates saved at order creation. The migration backfills `cod_amount` on existing orders using the buyer-payable formula. Snapshot rates and `money_status` stay null on legacy orders, and null `money_status` means the order predates cash tracking.
- `order_shipping_settlements.vendo_commission`: Vendo's share of the delivery fee, default 0. Written by the per-parcel split for orders that carry rate snapshots; older settlements keep 0.
- `order_cod_collections`: one row per delivered order with the amount the Rider collected, Rider, Station Hub and a unique scan key.
- `cash_remittances` and `cash_remittance_items`: one row per cash handoff (`rider_to_station`, `station_to_province`, `province_to_company`, `company_to_vendo`) and the orders in it. An order can appear once per level, so the same cash cannot be counted twice.
- `cash_remittances.resolution_note`, `resolved_at`, `resolved_by` (migration `2026_10_28_130000_add_resolution_to_cash_remittances.php`): how and by whom a Station Hub resolved a cash discrepancy.
- There are no seller payout tables. Vendo has no bank or e-wallet payout, so Seller earnings are calculated from the order (item total and the seller commission rate snapshotted on it) and shown on the Seller page.
